## 音量观察的准确范围

在独立浏览器中启用媒体 volume 赋值和 AudioContext.createGain 观察，浏览器通过 --mute-audio 静音输出，页面的 JS muted／volume 属性保持原逻辑。两条对应音源都处于网页播放器运行状态，原始作品音量参数不同，观察到的播放器音量都为 0.5，未观察到 createGain 创建的节点。

该方法没有测量实际输出响度，也没有覆盖直接 new GainNode、音频已含增益、其他处理节点或手机端实现，不能推出 110 必须变成 1.1 倍，更不能推出音量参数可以删除。实现先保留 gainRaw、记录未确认状态，按全局音量播放；需要完整复现作品增益时另补手机或经过验证的播放链证据。[GainNode 说明](https://developer.mozilla.org/en-US/docs/Web/API/GainNode)

## 续传：不能只信 If-Range

对首轮 FALA SÉRIO 音源作有界请求并取消响应体，没有重新保存整首文件：

| 请求 | 实际结果 |
| --- | --- |
| bytes=0-1023 | 206，Content-Range 为 0-1023/471324，返回强 ETag |
| bytes=1024-2047，匹配 If-Range | 206，范围正确，返回同 ETag |
| bytes=1024-2047，故意错误 If-Range | 仍是 206，范围正确，返回实际 ETag |
| bytes=999999999- | 416，Content-Range 为 */471324 |
| bytes=-1024 | 206，尾段 470300-471323/471324 |

标准定义条件不成立应回完整 200；这个 CDN 样本没有按该条件回退。记录的是特定地址的当天行为，不外推所有 CDN 都如此。[If-Range 规范说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Range)

客户端每次接收 206 必须比较实际响应 ETag／可信资源版本、总长度和请求起点；缺少可靠版本不跨会话拼接。错误版本、错误范围、200 整文件不能直接追加旧尾部；416 先核对是否已有完整对象，不自动把旧部分标成成功。服务器可能忽略条件，因此“已发 If-Range”不是文件未变的证明。完成后仍核对完整对象哈希、长度和格式。

## 文件验证实验

以真实 471,324 字节 AAC/M4A 作以下试验，原件不变：

| 例子 | 结果 |
| --- | --- |
| 文件名改为 .mp3 | 仍识别为 AAC/M4A，完整解码成功；说明扩展名不能作格式依据 |
| 只保留一半字节 | 长度／哈希不同，完整解码失败，不可声明已保存 |
| HTML 页面命名为音频 | 格式解码失败，不能把登录或错误页写入正式配乐 |
| 全部字节损坏但长度保持不变 | 长度相同、哈希不同、解码失败，不能只检查文件存在和大小 |

源首次取得时若没有预期内容哈希，必须以可靠传输结束、已知长度（若有）、实际格式及结构／解码验证构成证明，然后登记自己的内容哈希；不能拿“文件自己的哈希算出来了”证明未截断。后续 NAS 恢复可以比较已有可信哈希。

## NAS 兼容：隔离服务实测

使用未改动的当前服务代码，在新建目录与本机回环地址运行；上传实际音频和小型图片测试对象，建立三条虚构作品。第三条专门只含实验性新哈希字段，用于证明错误接入方式的后果，不是用户真实作品。

1. 两条作品的旧 downloads.assets 可引用同一个 audio SHA；服务对象只有一份，提交回执内容摘要匹配，相同 requestId 重试不重复增加提交。
2. 在 requiredKeys 中加入 audio，会被当前服务以 400 拒绝；新增 shared_audio 记录类别也被拒。
3. 当前客户端恢复这两条测试作品时，分别写入两个作品目录的 audio.m4a，实际产生两份本地文件，没有形成共享本地存储。
4. 删除一条测试作品，另一条清单还引用时，音频对象保留。
5. 删除第二条后，第三条作品里仅存的新 musicInfo.objectHash 没有被当作有效引用，测试音频被回收，第三条哈希仍在。此结果说明拟议新字段不能单独接入旧 GC，并不表示当前正常备份已经发生这种错误。
6. 当前服务没有 sharedAudio 能力声明。因此仅凭 assets 接受 kind=audio，不能宣称已支持完整配乐功能。

可重复运行的研究脚本：`node scripts/research-audio-nas-compatibility.mjs`。需要首轮音频证据文件仍存在；只建立新的本机测试服务，绝不使用用户 NAS 连接配置。运行会在隔离测试库中执行删除／回收案例，不清理现有测试或用户目录。

## 拟定实现路线

### 数据与状态

采用精简作品音乐元数据、共享音源内容对象、作品片段、来源提示、本机保存意图和 NAS 保存状态分层。原始 begin/end/volume 与确认状态保留；未知字段不覆盖有效旧信息。签名音频地址放在有期限的本机来源提示里，不成为每轮日志或版本主键，不重复同步整库获取历史。

区分：明确无音乐、信息未知、有条目但无可用地址、音源可试听但片段未知、配乐已正式保存、NAS 已确认、对象暂缺。false 标记、-1 参数、无地址或单次接口错误都不单独证明“无音乐”。音频缺陷和图片完整状态独立，升级不让已有几万图文变成下载失败。

### NAS 格式选择与兼容门槛

优先评估在现有下载清单中增加独立 `audio` 部分，保存验证过的对象引用和音频状态；继续让 `assets`／`requiredKeys` 表达既有图片、视频必需文件。服务端必须新增严格校验、GC 引用扫描、音频仅存时的删除处理和能力声明。避免为了配乐先引入许多新记录类别，也不把新共享路径塞进现有单作品目录规则。

这是设计选择，未修改服务。启用前需要配套的新服务与客户端，并测试：

- 新客户端只在服务明确支持共享音频时上传引用；不支持时音频留在本机或待备份，不显示 NAS 已成功保存。
- 新服务在库启用音频新格式后，必须阻止旧客户端覆盖相关记录；允许旧客户端只读时，还要验证它能解析基础作品／图片记录。不能只加能力字段而让旧客户端照常写入。
- 删除 NAS 图文备份要解除该作品音频保存引用，保留其他作品的引用；音频仅存、图片为空的作品也必须能删除。作品音乐元数据保留不等于对象永久被引用。
- 提交确认、回执未知、同库匹配、音频共享删除、并发变更和多电脑恢复都通过后，才开放仅 NAS 保存。协议号是否保持 2 由兼容测试决定，不提前承诺无需服务升级，也不要求清空现有 NAS。

### 共享文件与缓存

本机共享音频要有专用资源解析器；播放、存在性检查、下载、恢复、删除和 NAS 分析都调用它。当前 asset 路径只允许作品目录，必须增加明确的共享音频范围，不能放开路径边界。长期保存和试听可复用同内容，但用途引用独立；清缓存不删永久媒体。

沿用建议的封面 768 MiB、试听 256 MiB、备份暂存 256 MiB 三个预算。先预留后写入，未知长度逐步申请，播放／待提交保护使额度无法满足时停止扩张。LRU 与占用摘要属于本机，不因试听触发 NAS 同步；不一次加载三万作品的全部音乐对象。

研究脚本 `scripts/research-audio-contract.test.mjs` 已验证 18 条规范模型，包括负值／未知单位、非零时轴、独立片段、边界约束、并发空间预留、三万次入队决策、正在使用／未完成／待提交保护、200／错误 206／版本变化拒绝追加。它们没有接入正式下载器或缓存模块，不能作为正式功能已经通过的证据。真实共享下载取消、断电恢复、磁盘满和两台机器性能仍要在实际实现中验证。

其中“三万次”只是小型内存账本的反复预留决策，不包含三万真实文件、音频解码或数据库操作，不外推成软件处理三万作品的速度。

### 保存引用、空闲规则与失败传播

“本地有什么就备份什么”在共享音频中必须按作品的正式本地保存引用判断：A 已取消本地保存、B 仍保留同一物理文件时，不能把 A 重新自动备份。删除 A 的 NAS 引用后，试听 A 不恢复永久保存意图；B 的本机与 NAS 引用继续有效。

空闲备份的判定应排除前台读取、媒体下载、检查／删除和正在取得音频的前台请求。已经使用本地文件播放时可允许低优先级备份，否则连续听音乐可能让 NAS 永久等待。后台 NAS 保存任务不能把自己算作“前台忙碌”而锁住提交；同一音源同时有前台与后台等待者时，暂停后台只解除后台等待，不中断前台声音。

来源超时、普通 403／404、NAS 断联或配乐缺失只影响对应音轨，不回滚图片、已提交读取页和作品记录；真实平台 429／账号失效仍遵守既有冷却和重连规则，不以音频实验或回退绕过限制。所有来源更新都核对当前作品与任务代次，快速切换后不得把旧响应绑定到新作品。

## 可以开始与仍需补证的工作

| 工作 | 准备程度 | 实施约束 |
| --- | --- | --- |
| 基础音乐字段、三态可用性、精简绑定索引 | 可开始分阶段实现 | 不在读取时请求全库音频；不以 false／-1 推断无音乐 |
| 缓存账本、共享对象、普通图文按需试听 | 有真实来源与规范模型依据 | 首次上线同时具备限额、取消、保护和未知状态；仍需正式回归及实机验收 |
| 本机正式配乐保存及按选补齐 | 可在共享解析器完成后推进 | 图片完整独立；不靠改名／文件存在性认定音频完整 |
| 非零片段精确还原 | 只有模型，缺少真实样本 | 暂不宣称平台非零时间一定对应同一音源坐标，取得样本后核对 |
| 多轨原声／配乐混音 | 未验证 | 不自行合成或只保存其中一轨冒充完整声音 |
| 手机端作品增益 | 未验证 | 原始参数保留，不直接乘 1.1 或删除它 |
| 登录必需的音源／收藏接口音乐字段 | 隔离会话未可用 | 后续通过正式程序当前会话做小样本观察，不清登录或复制凭据以强行完成 |
| 无音乐、不同音乐 ID 相同音频 | 未找到对应真实样本 | 保留明确未知状态；不同 ID 去重只有完整哈希证据才合并 |
| 完整 NAS 保存、多电脑迁移 | 已找出当前兼容障碍，尚未实现修复 | 服务／客户端能力、引用回收、旧客户端保护和共享恢复共同验收 |

本轮并未完成全部边界验证。下一轮优先补少量非零片段、混音及手机端对照样本；不通过请求三万条作品来碰运气。此文件和 JSON 保存了继续入口，后续实施应引用实际模块完成记录，不把研究模型和正式代码混为一体。
