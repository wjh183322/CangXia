# 藏匣服务版 CangXia Server

正式代码开发分支为 `codex/server-edition-full`。它从试验分支 `codex/server-edition` 的提交 `e2ac5b10f8f7df2eb6e1966558ba54e5a8948e59` 分出。[完整版设计（待审阅）](../superpowers/specs/2026-11-26-full-server-edition-design.md)

正式版版本号从 `0.4.1` 开始。此前的 `0.4.0-alpha.1` 属于可行性试验。

正式版日常部署使用 `ghcr.io/wjh183322/cangxia-server:latest`。这是目标发布地址，待首版通过发布验收后启用。每次发布同时保留编号标签，首版为 `0.4.1`；新装和常规更新在 Docker 项目中拉取最新版并重新部署，故障回退使用上次记录的镜像摘要及兼容的数据快照。

## 基线与定位

从藏匣备份版 `0.3.46` 的提交 `08e6436522a3828211e9c32b51f90d7d830b4fa8` 创建。本版本区别于既有 `codex/nas` 上的藏匣NAS版 `0.2.1`，也不以更早的默认 main 作为业务基线。

目标是 NAS 负责采集、唯一正式资料库、媒体和持久下载，Windows 负责原有操作界面与可清理缓存。任意电脑建立会话后只采用 NAS 当前状态与进度；存在其他有效使用会话时禁止进入，不跨会话补交旧电脑的数据。

## 成品兼容原则

除已确认的架构差异和缺陷修复外，正式成品的界面、操作习惯与业务逻辑按当前备份版对齐，保留读取顺序、筛选排序、字段、归属、目录整理、下载补齐、单图与可靠高清匹配、图文视频和配乐等能力。测试控台可以简化，不作为正式界面交付，不以重构为由取消原有功能。

## 验证和交付

先准备独立可行性验证原型，在隔离数据与指定样本上验证真实 NAS 的登录、来源字段、完整页事务、独占、异常恢复、下载和性能。验证结果决定是否进入正式产品实施；未测项目不记为通过，不直接迁移正式资料。

NAS 部署采用完整预构建镜像，从镜像库拉取并通过一个应用项目启动，不要求用户复制源码、安装依赖或构建镜像。

GitHub Actions 在 `codex/server-edition` 上构建并检查 Linux amd64 试验镜像，预留 GHCR 包名 `ghcr.io/wjh183322/cangxia-server-probe`。标签绑定版本和提交，部署绑定经核对的镜像 digest。构建工作流在临时 runner 加载镜像、运行合成测试并记录脱敏结果。镜像检查覆盖合并后的文件系统，也逐层检查基础镜像之后新增的文件头，包括后来被删除或覆盖的文件。镜像发布、包可见性和拉取权限单独确认。正式镜像名预留为 `ghcr.io/wjh183322/cangxia-server`。

### NAS 测试镜像更新

现有测试项目可一次性使用 `ghcr.io:443/wjh183322/cangxia-server-probe:preview`。将这个引用写入 Compose 后，后续在绿联重新部署时勾选「拉取最新镜像」，数据挂载和其他配置继续沿用原项目。

发布试验镜像时先保留版本和提交对应的编号标签，并通过 Linux、镜像审查和实际运行检查。仅将 `preview` 指向通过这些检查且已发布的镜像摘要，发布后核对两者的清单摘要一致。记录每次实际部署的摘要，回退时选原来的编号镜像并按摘要固定。普通开发提交不移动测试标签。

## 当前状态

2026-11-26，独立原型在真实 NAS 上完成扫码账号核验、作者采集计时和读取中的客户端交接。按已测范围进入正式版开发，继续以备份版为业务对照。

| --- | --- |
| run-06 扫码及重启恢复 | 镜像 `0.4.0-alpha.1-59897ea29f51` 在 NAS 加载登录组件 4.0.8。从打开登录页起，6.53 秒识别面板，7.83 秒二维码请求送达，36.49 秒完成账号核验。重启主容器后，直接核验返回同一 UID。此前 21.35 秒送达的慢请求在本地受控测试复现并通过，成功的 NAS 扫码样本耗时较短。 |
| run-06 非零游标交接 | NAS 上的固定样本两项均通过。第 1 页已提交、第 2 页尚未发出时，接手方从已提交游标发送一次；第 2 页已发出时，接手方等待原请求结束，再完成同一作业。共享作品的两个收藏夹归属均保留，已有图片只下载一次。 |

| 读取中交接 | 第一个客户端在读取中、首个完整页提交前释放使用权。旧客户端随后被拒绝访问，新客户端在旧读取结束前收到忙碌响应，随后用同一作业和保存的游标继续，提交 2 页、54 个作品后达到样本上限。 |

本轮登录没有出现强制短信验证。两个客户端在同一台 Windows 上运行。成品 Windows 界面、真实双机睡眠恢复、异地使用和正式资料迁移回退仍须在发布切换前验收。

开发和后续相关工作流只在本分支推进，保护现有 main、备份版及旧 NAS 分支。不得提交用户资料库、媒体、恢复副本、登录会话、令牌、真实采集响应或个人调查附件。

## 本地验证记录

原型位于 feasibility/nas-b，包与依赖锁独立。真实现场表和验证附件放入已忽略的 .evidence/，公开说明只记录脱敏结论。

配置检查要求显式试验模式、专用根目录及匹配的试验标识。NAS 的实际宿主挂载、端口可用性、运行身份和资源余量由部署前的现场核对确认。缺少现场输入时暂停部署。

业务和后续正式界面对照沿用备份版 0.3.46 的源码、现有测试及相同窗口尺寸、显示缩放。验证控台、试验样本上限及测试网络配置仅用于可行性验证。

## 容器检查和现场配置

构建使用固定的 Playwright Noble amd64 镜像清单。容器内含匹配的 Playwright Core、Chromium、Xvfb、OpenSSL、FFmpeg/ffprobe、Node/SQLite 和 CPython 3.12 的 OpenCV/NumPy wheels。Ubuntu 工具由安装包分发，Python 依赖锁校验固定 wheel 的 SHA256。Node、Python 和系统包的许可证保留在发行包目录中。

CI 的完整应用使用非 root、只读容器文件系统和独立试验挂载，以临时 HTTPS 证书自检。独立夹具挂载运行文件原子操作测试。Linux runner 上的结果和 NAS ext4 上的现场结果分别记录。

在 `feasibility/nas-b` 可运行 `npm run test:delivery` 检查构建和交付边界。 `render-deployment.mjs` 从标准输入读取审核过的现场参数及发布证明。现场尚未确认或镜像尚未验证可拉取时只报告受阻项。生成的包包含一个 Compose 项目和 Chromium 沙箱的 seccomp 文件。使用 Moby 固定版本的默认拒绝配置，增加 Playwright 建议的用户命名空间调用，并允许 Chromium 沙箱发起由 Linux 按命名空间核验权限的 `chroot`。容器保持非 root 并移除外层 capabilities。需要 NAS 的运行时支持该配置与用户命名空间。 [Moby seccomp 配置](https://github.com/moby/profiles/blob/9ee3204f0d0cfa19ca2c6a7b0fcf5a2b353954ae/seccomp/default.json) [Playwright Docker 文档](https://github.com/microsoft/playwright/blob/v1.65.1/docs/src/docker.md)
