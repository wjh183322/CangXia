# 藏匣服务版 0.4.1 候选装机与验收

Windows 用户选 `CangXia-Server-0.4.1-Setup-x64.exe` 安装，或直接运行 `CangXia-Server-0.4.1-Windows-x64.exe`。核对同次构建的 candidate.json 中 SHA-256、版本和完整提交。候选仅用于已获准的独立环境。镜像可见性、真实 NAS 验收与正式发布由所有者分别确认。

## 首次部署

1. 从同次构建的部署包解压 `compose.yaml`、`chromium-seccomp.json` 和许可证到同一项目目录。服务需要支持此 seccomp 配置、非特权用户命名空间的 Linux amd64 Docker。为容器保留 512 MiB 共享内存，另为浏览器、视频与数据库留出 RAM 和磁盘。
2. 在 NAS 文件管理器创建三个**全新且彼此独立**的目录，分别用于正式资料、服务身份、彩排。避免共享根目录、旧备份、已还原文件夹和相互嵌套的路径。将目录所有者设为运行服务的专用 NAS 用户，设为仅所有者可读写进入（Linux 0700），取消继承的共享访问。确认该用户的数字 UID、GID。若文件管理器不能设置所有权与独占权限，请 NAS 管理员通过存储管理界面准备这些目录。服务不会替管理员批量改权限。
3. **仅在首次建新库**，在资料目录和身份目录内各新建一个名为 `CREATE-NEW-CANGXIA` 的空文件夹。保留彩排目录为空。服务只会在这两个独立目录均含有该唯一标记、权限与挂载均符合要求时生成新库、证书和设备凭据。中断后保留残留目录，先从管理界面检查。重新试装使用另一组全新目录。
4. 在绿联 Docker 的「项目」中导入 Compose。项目路径选择解压目录。在项目环境变量表填写下表。没有环境变量表时可在 Compose 编辑器用对应实际值替换 `${…}` 项（地址、目录与镜像保留引号）。通过 HTTPS 直连或既有安全远程网络访问；记录最终可达的地址和端口。
5. 候选试装使用已经获准且可拉取的编号引用，优先完整摘要。确认仓库权限和登录后，在项目中拉取并部署。正常运行显示 healthy。重启后应保留原库身份、证书和设备文件。错误或空挂载、意外 schema、证书或文件权限错误时先查项目日志，保留原有挂载和数据。
6. 从 NAS 管理员私有文件管理界面打开身份目录中的 `identity/windows-1.json`，将 `url`、`deviceId`、`fingerprint`、`token` 分别填入第一台 Windows 客户端。第二台使用 `windows-2.json`。通过可信渠道单独核对 SHA-256 指纹。每台设备只取自己的文件，私钥与 devices.json 留在受保护目录。证书变化时从管理员重新取得的证书记录独立核实，再在连接页更换指纹。服务凭据和抖音官方登录分别办理。

| 项目环境变量 | 值 |
| --- | --- |
| CANGXIA_LIBRARY、CANGXIA_CONFIG、CANGXIA_REHEARSAL | 三个已创建目录的 NAS 完整宿主路径 |
| CANGXIA_UID、CANGXIA_GID | 上述目录所有者的数字 UID 和 GID，默认 1000 |
| CANGXIA_URL | 客户端访问地址，例如 `https://nas.example:9443` |
| CANGXIA_PORT | NAS 对外端口，默认 9443 |
| CANGXIA_IMAGE | 常规部署默认 `ghcr.io/wjh183322/cangxia-server:latest`。候选部署填写所有者提供的 `ghcr.io/wjh183322/cangxia-server@sha256:…` |

## 更新、绿联备份与隔离还原

更新前记下原镜像摘要、资料库 UUID 和证书指纹。先停止新的读取、下载和整理并等待已确认写入落盘，保全当前数据库及同一时点的完整归档。保持三个挂载、UID、身份不变，拉取目标镜像后重新部署。普通重启不会批准 schema 迁移。若日志提示版本不符，停止项目，改回原兼容镜像摘要。升级或切换已有数据前另行彩排与批准。

1. 在 Compose 项目环境中填 `CANGXIA_SOURCE_UID`（已核对的抖音数字 UID）与 `CANGXIA_DEPLOYED_DIGEST`（当前已部署镜像真实清单的 `sha256:…`）。重新部署后，服务在独立彩排区准备目录与受保护的账号配置。不要用 Windows 设备号或 Docker 配置摘要代替这两个值。
2. 在 Windows 的数据管理/备份页进入迁移彩排，选择「运行库回退前移交」。填新的目标名称、核对库与账号，等待完成，保存报告中的数据库快照路径、媒体归档路径、库 UUID 与清单 SHA-256。把报告和摘要独立保管。用绿联备份工具把该快照目录及同一恢复点的完整媒体归档备份到独立介质，同时单独保护服务身份目录。报告反映核对时的内容，涉及写入的任务应持续暂停至绿联完成备份。
3. 用绿联把快照与媒体**还原到独立暂存目录**，例如彩排区 `restores/usb01/snapshot/`、`restores/usb01/media/`。把原报告的库 UUID、清单摘要分别填入项目环境 `CANGXIA_RESTORE_LIBRARY`、`CANGXIA_RESTORE_SHA256`，将 `CANGXIA_RESTORE_NAME` 设为 `usb01`。服务只登记该恢复点；同名不同摘要会拒绝启动。需要其他恢复点时使用新名称。
4. 重启项目，选该恢复名称并点击核对。查看匹配、缺失、变动、额外文件、业务记录和任务。在报告无差异后选择新的目标名，再批准「验证独立恢复库可用性」。程序复制到独立目标、重建文件身份，并通过正式播放接口读回。保留旧卷、回收记录、恢复报告和切换后新增资料。正式挂载切换须另行取得批准。
5. 旧 Windows/旧 NAS 迁移涉及多个同一时点的输入及设备删除证据。先由管理员按迁移指南制作只读一致副本和已核验封存清单，再从同一彩排页面预览。首次装机和普通备份还原无需在 NAS 编译程序。见[迁移彩排指南](migration-rehearsal.md)。

## 编号候选与正式发布

开发分支 push 仅构建、运行隔离测试并在 Actions 保存限时工件。获取部署包不需要将源代码复制到 NAS。构建成功也不会修改 GHCR 标签。

维护者在具有 gh、skopeo、jq 的受信 Linux 电脑登录 GitHub 与 GHCR，先取得包可见性及编号发布许可。执行仓库中的 `bash scripts/promote-server-image.sh candidate <成功的运行编号> <完整提交>`，复核运行、标签和清单后按提示输入批准。工具校验 CI 的 OCI 包、源标签与清单，只推该次版本候选。待现场项目通过并另行取得正式发布许可，再用同一组输入运行 `stable`。它要求相同候选摘要，将编号 0.4.1 和 latest 指向该清单，分别从注册表回读验证。一次只由一位发布人操作。私有/公开与用户名额由所有者管理。
