# 藏匣服务版 0.4.1 候选装机与验收

Windows 用户选 `CangXia-Server-0.4.1-Setup-x64.exe` 安装，或直接运行 `CangXia-Server-0.4.1-Windows-x64.exe`。核对同次构建的 candidate.json 中 SHA-256、版本和完整提交。候选仅用于已获准的独立环境。镜像可见性、真实 NAS 验收与正式发布由所有者分别确认。

## 首次部署

1. 从同次构建的部署包解压 `compose.yaml`、`chromium-seccomp.json` 和许可证到同一项目目录。服务需要支持此 seccomp 配置、非特权用户命名空间的 Linux amd64 Docker。为容器保留 512 MiB 共享内存，另为浏览器、视频与数据库留出 RAM 和磁盘。
2. 在 NAS 文件管理器创建四个**全新且彼此独立**的目录，分别用于正式资料、服务身份、彩排输出及管理员批准的只读输入。避免共享根目录、旧备份、已还原文件夹和相互嵌套的路径。前三个目录的所有者设为运行服务的专用 NAS 用户，设为仅所有者可读写进入（Linux 0700），取消继承的共享访问。确认该用户的数字 UID、GID。若文件管理器不能设置所有权与独占权限，请 NAS 管理员通过存储管理界面准备这些目录。第四个目录须由另一位 NAS 管理员所有，仅给服务账号读取与遍历权限，创建 sources、manifests、restores 三个子目录。保持 Compose 的 /approved 只读挂载，原件和管理员批准文件都在此处，不能复用前三个目录。
3. **仅在首次建新库**，在资料目录和身份目录内各新建一个名为 `CREATE-NEW-CANGXIA` 的空文件夹。保留彩排输出目录为空。服务只会在这两个独立目录均含有该唯一标记、权限与挂载均符合要求时生成新库、证书和设备凭据。中断后保留残留目录，先从管理界面检查。重新试装使用另一组全新目录。
4. 在绿联 Docker 的「项目」中导入 Compose。项目路径选择解压目录。在项目环境变量表填写下表。没有环境变量表时可在 Compose 编辑器用对应实际值替换 `${…}` 项（地址、目录与镜像保留引号）。通过 HTTPS 直连或既有安全远程网络访问；记录最终可达的地址和端口。
5. 候选试装使用已经获准且可拉取的编号引用，优先完整摘要。确认仓库权限和登录后，在项目中拉取并部署。正常运行显示 healthy。重启后应保留原库身份、证书和设备文件。错误或空挂载、意外 schema、证书或文件权限错误时先查项目日志，保留原有挂载和数据。
6. 从 NAS 管理员私有文件管理界面打开身份目录中的 `identity/windows-1.json`，将 `url`、`deviceId`、`fingerprint`、`token` 分别填入第一台 Windows 客户端。第二台使用 `windows-2.json`。通过可信渠道单独核对 SHA-256 指纹。每台设备只取自己的文件，私钥与 devices.json 留在受保护目录。证书变化时从管理员重新取得的证书记录独立核实，再在连接页更换指纹。服务凭据和抖音官方登录分别办理。

| 项目环境变量 | 值 |
| --- | --- |
| CANGXIA_LIBRARY、CANGXIA_CONFIG、CANGXIA_REHEARSAL | 前三个已创建目录的 NAS 完整宿主路径 |
| CANGXIA_APPROVED | 第四个目录，由独立管理员所有，服务只读，放置封存来源、清单、恢复副本及可选 rehearsal.json |
| CANGXIA_UID、CANGXIA_GID | 上述目录所有者的数字 UID 和 GID，默认 1000 |
| CANGXIA_URL | 客户端访问地址，例如 `https://nas.example:9443` |
| CANGXIA_PORT | NAS 对外端口，默认 9443 |
| CANGXIA_IMAGE | 常规部署默认 `ghcr.io/wjh183322/cangxia-server:latest`。候选部署填写所有者提供的 `ghcr.io/wjh183322/cangxia-server@sha256:…` |

## 更新、绿联备份与隔离还原

可恢复文件删除默认关闭。只有绿联针对该机型和文件系统明确支持按原相对路径独占移动与恢复，并提供回收映射时，才使用专用共享目录。将该共享目录作为唯一的 `CANGXIA_LIBRARY` 绑定，创建私有的资料子目录，在 `CANGXIA_LIBRARY_CHILD` 中填写这个子目录名。在 `CANGXIA_NATIVE_RECYCLE_RELATIVE` 中填写管理员独立核实的厂商回收映射相对路径。首次新库标记放在资料子目录内。该共享目录只容纳这一套资料及其回收目录；其他用户数据、额外绑定及子挂载均不适用于此布局。服务账号还须具备所需目录权限。

在 Windows 的删除设置进行现场验证，填写支持依据、实际保留期；用绿联原生回收界面还原专用样本，再由服务核验身份、SHA-256 及双向独占移动。绿联没有提供受支持的映射、原生界面没有显示并原位还原样本，或挂载发生变化时，保留原件，重新核对。CI 的 Linux 受控目录只测试容器内的移动语义。

更新前记下原镜像摘要、资料库 UUID 和证书指纹。先停止新的读取、下载和整理并等待已确认写入落盘，保全当前数据库及同一时点的完整归档。保持四个挂载、UID、身份不变，拉取目标镜像后重新部署。普通重启不会批准 schema 迁移。若日志提示版本不符，停止项目，改回原兼容镜像摘要。升级或切换已有数据前另行彩排与批准。

1. 在 Compose 项目环境中填 `CANGXIA_SOURCE_UID`（已核对的抖音数字 UID）与 `CANGXIA_DEPLOYED_DIGEST`（当前已部署镜像真实清单的 `sha256:…`）。重新部署后，服务在独立输出区准备 targets、reports，并从管理员的只读配置或已批准 Compose 环境值核对账号。不要用 Windows 设备号或 Docker 配置摘要代替这两个值。
2. 在 Windows 的数据管理/备份页进入迁移彩排，选择「运行库回退前移交」。填新的目标名称、核对库与账号，等待完成，保存报告中的数据库快照路径、媒体归档路径、库 UUID 与清单 SHA-256。把报告和摘要独立保管。用绿联备份工具把该快照目录及同一恢复点的完整媒体归档备份到独立介质，同时单独保护服务身份目录。报告反映核对时的内容，涉及写入的任务应持续暂停至绿联完成备份。
3. 用绿联把快照与媒体**还原到独立暂存目录**，例如第四个只读输入区的 `restores/usb01/snapshot/`、`restores/usb01/media/`。把原报告的库 UUID、清单摘要分别填入项目环境 `CANGXIA_RESTORE_LIBRARY`、`CANGXIA_RESTORE_SHA256`，将 `CANGXIA_RESTORE_NAME` 设为 `usb01`。服务只登记该恢复点；同名不同摘要会拒绝启动。需要其他恢复点时使用新名称。
4. 重启项目，选该恢复名称并点击核对。查看匹配、缺失、变动、额外文件、业务记录和任务。在报告无差异后选择新的目标名，再批准「验证独立恢复库可用性」。程序复制到独立目标、重建文件身份，并通过正式播放接口读回。保留旧卷、回收记录、恢复报告和切换后新增资料。正式挂载切换须另行取得批准。
5. 旧 Windows/旧 NAS 迁移涉及多个同一时点的输入及设备删除证据。先由管理员按迁移指南制作只读一致副本和已核验封存清单，在管理员输入区放置 sources、manifests 及 rehearsal.json（accountId 取自 NAS 身份目录 devices.json 中同名字段）。重新部署后，从同一彩排页面预览。首次装机和普通备份还原无需在 NAS 编译程序。见[迁移彩排指南](migration-rehearsal.md)。

## 编号候选与正式发布


普通开发分支推送只构建、实测并在 runner 本地封存镜像。公开仓库的 Actions 只保留两个小型构建记录（源码、版本、协议与内容摘要）。Windows EXE、部署 ZIP、完整 OCI 镜像和用户文件均不会随普通 CI 上传。

**所有者批准编号候选。** 先核对正式开发分支一次成功 push 构建的运行编号和 40 位源码提交。所有者在 GitHub 或自己的 Git 客户端创建一个新的轻量标签，精确指向该提交。标签名为 `server-candidate-<private或public>-<成功分支构建运行编号>-<40位提交>`。此标签是对该可见性和编号候选分发的显式授权。专用 GitHub runner 核对触发人、来源运行与提交，重新构建、审查并在容器里测试**本次将发布的同一个镜像**。它校验实际 Docker v2 清单、配置和源码标签，只将编号 `0.4.1-rc.<候选运行编号>.<尝试号>` 写入 GHCR，并从注册表读回核对。记录候选运行号、尝试号、实际清单 SHA256 和源码提交。普通 CI 的较早构建不提供后续二进制分发输入。

容器包必须具有标签明确批准的可见性。若包尚不存在，流程仅尝试写入一个没有任何产品文件的空镜像以建立包名，随后读取 GitHub Packages 实际可见性。与预期不符时停在分发前，由所有者在包设置核对访问范围，再重新运行获准的流程。不会自动修改包可见性。私有候选的 Windows 包由持有人从本地成品目录通过已核准的私有渠道交付；公开仓库 Actions 不保存这些 EXE。只有显式批准 public 候选、注册表核验成功后，才在同次运行上传验过安装启动的公开 Windows 包和部署 ZIP。独立的最终任务核对适用于该可见性的所有步骤。公开候选若 Windows 打包、实际启动或上传失败，即使镜像已存在，也不会取得允许正式提升的提交状态。私有候选则要求公开 Windows 分发任务确实跳过。[GitHub 容器可见性](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)

**单独批准正式提升。** 现场验收与正式发布许可均已具备时，在原提交创建新的轻量标签 `server-stable-<private或public>-<候选运行编号>-<尝试号>-<清单64位小写十六进制>-<40位提交>`。维护者可在 GitHub 的提交状态中核对 `cangxia-server/candidate/<运行编号>/<尝试号>/<可见性>` 以及该记录中的镜像摘要。runner 校验 GitHub Actions 账户写入该提交的成功状态、运行链接、可见性、不可变镜像摘要和对应编号候选。它从已存在的注册表摘要直接建立 0.4.1 和 latest，并分别回读验证。此前运行的工件或日志到期不影响提升。服务镜像不会在提升时重建，已有其他内容的 0.4.1 标签会阻止替换。没有该独立所有者批准时不会移动 latest。
