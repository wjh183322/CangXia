# 客户端批量下载与响应性优化设计

日期：2026-10-28。状态：独立审查完成，用户已确认；进入实施计划，尚未实施。

代码基线：`08e6436522a3828211e9c32b51f90d7d830b4fa8`，桌面端 0.3.46。本文不要求 NAS 服务升级。

## 1. 目标与已确认范围

用户报告：全选 32,585 个作品，在“下载所选作品”弹窗点击“只下载未保存的 775 个”后，Windows 显示窗口未响应。平时无后台任务的浏览卡顿不明显。

用户选择 A＋有针对性的 B：先消除重复工作，再把仍需耗时的分析与窗口响应隔离。优先修复批量下载，同时检查浏览、搜索、选择和状态刷新；不借此重写整个客户端。

目标：

- 数万条历史记录下，批量下载准备期间仍可操作窗口、查看进度、请求停止。
- 本次下载范围保持明确，不因优化重新加入已完整保存或已失效的作品。
- 原有文件保护、断点续传、暂停、取消清理、收藏顺序、读取计数和 NAS 删除版本规则继续成立。
- 正常浏览不因下载进度反复重算整个资料库；新增后台服务的 CPU、内存、通信与生命周期有界。
- 报告实际测量与未覆盖部分，不把自动化结果当作遵义电脑实机验收。

非目标：浏览器版、NAS 直接下载、永久处理历史功能、NAS 数据布局迁移、SSD 缓存配置、抖音接口策略调整。本轮不更改收藏读取的新增计数，也不删除功能来缩小安装包。

## 2. 调查证据及其边界

### 2.1 已复现的问题

现有调用链：

`src/main.jsx submitDownloads` → `main.mjs download` → `planDownloads` → 排除旧任务 → `DownloadQueue.enqueue` → `createCancellationOwnership` → `Store.destination`。

在没有可直接复用的备份目录归属时，`Store.destination` 使用 `this.all('downloads').some(...)` 判断目录冲突；`Store.all` 会读取和 JSON 解析全部下载记录。每个新任务都可重复执行这一步，复杂度约为新任务数乘以历史下载记录数。`enqueue` 另有逐 ID 扫描整个任务列表的检查，且整个入队过程没有让出事件循环。

隔离模拟调用现有代码，31,542 条历史下载清单，每条 4 个资源，未联网、未下载、未写作品文件：

| 新任务数 | 全清单解析次数 | 解析记录总数 | 同步占用时间 |
|---|---:|---:|---:|
| 1 | 1 | 31,542 | 111 ms |
| 5 | 5 | 157,710 | 489 ms |
| 20 | 20 | 630,840 | 1,935 ms |

时间是本机模拟测量，不是用户电脑耗时；不把线性外推当作实际 775 项用时。已有可靠 `home` 的作品可能绕过该路径，因此也不认定所有作品都执行相同数量的扫描。证据足以确认一个可导致未响应的缺陷，不代表所有卡顿均已定位。

### 2.2 需要一起审计的路径

- `main.mjs` 在下载提交前后重复规划，可能先批量移除旧任务。
- `download-tasks.mjs` 的整队替换、排序、持久化与入队检查。
- `download-cancel-cleanup.mjs` 的文件保护快照及有产出任务的共享文件核对；无产出任务已有跳过全库扫描的优化，应保留。
- `snapshot-feed.mjs`、`work-views.mjs`、`state-patch.mjs` 的资料版本与运行进度更新。
- `src/main.jsx` 的筛选请求、跨页全选、选择集合和列表派生数据。

现有 `file-state-worker.mjs`、`repair-check-worker.mjs`、`backup-analysis-worker.mjs` 使用 `worker_threads`。它们能隔离事件循环，但不是独立操作系统进程；不得把它们描述为完整的进程故障隔离。现有增量快照、分页任务列表和搜索索引继续复用。

## 3. Approaches：备选方案与选择

| 方案 | 收益 | 代价 | 结论 |
|---|---|---|---|
| A：索引复用、批量处理、协作式分段 | 减少实际工作量，改动集中 | 真正重的同步分析仍可能阻塞主进程 | 必做的第一层 |
| B：大范围重构为独立后台进程 | 更广泛的故障及事件循环隔离 | 重做写入协调、生命周期和任务协议；可能复制整库而增加内存 | 本轮不采用全面迁移 |
| A＋有边界的 B | 消除低效后，把必要的全库分析隔离；保留成熟写入与清理流程 | 增加一个小型只读后台服务和版本校验 | 用户选择，本文采用 |

本轮 B 的具体落点由设计提出：大库下载准备所需的目录占用分析使用一个按需启动的独立辅助进程。小批、小库可以使用同一契约的分段实现。文件检查、备份分析沿用已有线程，不同时迁移。浏览分析若没有测得超预算，不为其新增进程。

## 4. 职责与数据边界

### 4.1 主进程

- 继续拥有正式 SQLite 连接、下载任务状态、NAS 连接、凭据、文件写入、取消清理及用户意图。
- 验证当前根目录、选中作品状态、下载来源、任务类型、文件归属与操作权限。
- 接收分析建议，核对版本后才创建任务；后台结果不能直接触发写入或删除。
- 大批量任务提交采用异步分段流程，不在一个同步 `enqueue` 内完成全部工作。现有普通下载、补齐、封面补齐及 NAS 恢复调用者均须适配，不能留下绕过新边界的入口。

### 4.2 只读分析辅助进程

- 使用 Electron `utilityProcess` 启动一个按需复用的辅助进程；这是独立进程，不把现有线程改名冒充 B。
- 只读取当前本机 SQLite 的已提交数据，主要提取下载记录 ID 与路径；不解析每条记录的全部媒体清单。
- 不打开写数据库连接，不执行下载、文件创建、移动、删除或 NAS 请求，不接收 Cookie、访问密钥、作品原始接口响应。
- 工作集是目录占用分析。按候选目录返回匹配的占用者、结果版本和必要的冲突信息；不得把全库清单或完整媒体列表发给主进程。
- 大库默认走辅助进程：初始阈值为历史下载记录达到 10,000 条；该阈值是设计建议，实施测量后可调整并记录理由。小库亦不得恢复逐任务全表扫描。
- 进程只按需启动；同一时刻最多一个分析请求，后续请求受控排队。空闲 30 秒可回收，大库索引内存随进程释放，不长期维持与主进程重复的作品库。
- 退出、崩溃、超时或协议错误时，当前准备操作显示失败及已受理数量；禁止自动退回到原来的同步全库扫描。

### 4.3 批次通信与版本

- 请求带唯一操作 ID、会话代次、根目录标识、资料库标识和选中 ID；候选目录、结果均分块传输。
- 默认每块最多 200 项或 256 KiB，先达到哪个就分块；一块收到确认再发送下一块，防止无界消息队列。单项超限须显式报错，不静默截断影响归属判断。
- 只读查询使用短事务/稳定数据库快照，不把等待主进程确认的整个时间都放在长读事务内，避免 WAL 无限增长。
- 主进程维护下载路径/归属专用代次：路径、根目录、相关来源或待处理占用改变才使结果失效；字节进度和不相关运行通知不应让分析持续重来。
- 应用重启后不复用旧进程结果；迟到回复按操作 ID 和会话代次丢弃。结果与当前资料不一致时停止发布或重算尚未受理部分，不覆盖当前文件归属。

一致性采取以下确定规则：辅助进程在一个已提交数据库读快照内建立紧凑的 ID/路径归属索引，结束读事务后才处理候选分块与等待 ACK；同一操作不从多个不同数据库快照拼接目录索引。请求携带主进程基准归属代次。主进程从该代次开始记录有界的路径变更覆盖层，包含本批自己的目录预留、受理结果及其他任务完成造成的已知路径变化；使用基准结果加覆盖层复核当前候选，不因本批每受理一片就重新构建全库索引。

已知的外部变化只使受影响候选重新核对；未变化候选继续。根目录、数据库身份变化，或变更代次有缺口、覆盖层已溢出而无法证明一致性，按整批中断处理，暂停尚未放行的受理项；新操作重新建立一次索引。不能悄悄使用旧结果，也不能无上限重建直到偶然成功。只读快照建立期间不等待主进程消费，数据库事务的实际时长需测量并纳入 WAL/退出验收。

## 5. A：下载准备与目录索引

### 5.1 一次分析，多次查询

- 对一次提交，只建立一次目录占用视图，不再为每个新任务执行 `all('downloads')`。
- 优先复用现有 `LocalReconcile.owners` 的规范化和多占用者语义；不要求复用其同步调用方式。
- 有可靠 `home` 的快速路径继续成立；作者来源、收藏夹归属、历史目录选择与长度限制保留。
- 同一批中确定的目标目录立即登记为批次预留，防止不同作品同名时都认为目录空闲。沿用现有命名及作品 ID 后缀规则。
- 索引只用于判断候选归属，不作为文件不存在、路径安全或可删除的证明。任务实际写入前仍复核当前目标和路径边界。
- 使用 `DownloadTasks.byId` 和状态集合完成任务查询；避免候选数量乘以队列长度的 `.some/.find` 链式扫描。

### 5.2 文件保护快照

- 每个新任务首次受理时记录它的原始文件/元数据保护快照，并在任何该任务写入前持久化。不能为了加速，把快照推迟到实际开始下载时才采集。
- 重试、暂停恢复和重复提交未完成任务沿用原来的任务 epoch 与快照，不重新建立“原有文件”基线。
- 同步目录遍历、文件读取改为有并发上限的异步检查；慢盘不能让主进程卡在大量同步 `readdir/lstat/readFile` 调用中。
- 采集期间同一作品及目标目录的冲突写入要受协调。根目录/路径变更会使当前快照失效；外部新出现或被替换的文件继续通过写入前跟踪与清理前身份复核得到保守保护。
- 目录预留不是写入许可；不得取消链接/越界检查，不能截断原始元数据备份来降低内存。异常或超限时保留文件并报告该项失败。

### 5.3 分段受理和停止

- 确认范围后立即发布“准备下载任务”状态，分段完成规划、快照和持久化。
- 主进程循环同时遵守条数和时间预算：初始每片最多 50 项或约 8 ms，先到即让出事件循环；单次 I/O 使用异步接口。不要用增加 `setTimeout` 掩盖重复全库工作。
- 准备中可浏览、搜索、翻页；允许只读详情查询。禁止同一选择重复提交，以及与受理范围冲突的删除、目录移动或根目录切换。
- 新任务在快照完整且持久化前不进入可执行状态。已准备但未放行的任务需要明确的批次标记，调度器不能提前执行。
- 正常完成后，受理任务分段放行到既有下载队列，继续使用原并发上限。
- “停止准备”停止尚未受理的部分；已持久化的新任务保留为暂停/未放行状态，不因停止准备清理文件。已有、与本批无关的运行任务不被停止。
- 准备中应用异常退出：重启后已受理的新任务保持暂停，用户可在下载管理继续；未受理部分不自动恢复。不能显示全部准备成功。
- 后续在下载管理显式取消这些任务，仍执行现有取消清理范围；停止准备与取消下载不是同一指令。

逐项失败与整批中断的调度规则如下：

| 情况 | 尚未受理项 | 已受理但未放行项 | 此前已经运行的无关任务 |
|---|---|---|---|
| 个别作品路径、快照等校验失败，剩余项目完成准备 | 失败项记录原因，不自动重试 | 成功项正常放行，结果标为部分完成 | 继续原调度 |
| 用户停止准备 | 停止处理，列明尚未受理数量 | 保持暂停，等待明确继续 | 继续原调度 |
| 辅助进程退出/超时、数据库忙、根目录改变或批次一致性无法确认 | 停止处理，报告整批原因 | 保持暂停，不能自动放行 | 不因本批失败取消它们；全局存储错误仍沿用原有保护 |
| 应用异常退出后重启 | 不自动重新创建 | 恢复为暂停，等待明确继续 | 沿用既有重启恢复规则 |

上述“已受理”同时包括新建任务和本批重试的原有失败任务；它们都保存独立的批次操作 ID 与未放行标记，不能只靠队列全局暂停实现。原有 waiting/running 任务视为已在队列，不接管、不重置其调度。重试已有失败任务仍保留原 epoch、文件保护快照和取消清理状态；本轮只是增加受理批次限制。

用户在下载管理明确继续已停止批次时，先复核当前根目录、路径预留、下载资格与未处于取消清理，再只解除该批次的未放行标记；不得顺便重试其他失败任务。复核失效的任务保持暂停并给出重新准备入口。重复提交命中未放行任务时指向现有批次，不创建新任务、不新采集保护基线。显式取消未放行任务依旧走原取消清理；清理完成才解除目录预留。

### 5.4 排除旧任务与兼容调用

- 预览统计和最终受理允许因资料变化不同，但必须明确返回实际受理、已有、跳过、失败、尚未受理数量。
- 已完整保存/已失效作品沿用原有排除规则。移除无需执行的旧任务时不能误走“显式取消并删除任务产物”而损坏已完整文件；应验证现有路径并保持“文件保留”的约定。
- 不因异步化更换来源：账号收藏下载仍为抖音下载，NAS 恢复仍使用 NAS；封面任务不混入普通媒体任务。
- 批次失败不能只出现“新增 0”；应显示具体阶段与可重试范围，重复操作不产生重复任务。

## 6. 日常浏览与状态刷新

本轮检查并做必要的小范围优化，不把没有测出问题的路径全面重构：

- 字节进度更新只更新运行摘要；不因任务进度重建作品数组、收藏关联、作者/标签选项或搜索索引。
- 库存变化才使对应资料派生数据失效；尽量保持未变化对象引用，继续使用现有增量快照和小页任务列表。
- 搜索输入适度合并请求，迟到回复不得覆盖当前查询。旧查询在可能时可取消；不能只在前端丢弃回复、后台仍无上限计算旧查询。
- 跨页全选和选择计数复用按资料/筛选版本建立的集合，不在每次下载进度通知时重新遍历全部作品。
- 原收藏顺序、大小排序、筛选语义、分页位置、选中作品范围、详情返回位置保持一致。
- 检查首次/热启动索引、筛选、翻页和批量期间的响应。只迁移确有阻塞的纯分析；不把正式数据库写连接搬给新进程。

## 7. 状态、退出与资源控制

准备操作至少区分：空闲、分析目录、准备保护快照、登记任务、停止中、完成、部分完成、失败。报告总数、已受理、跳过、失败和尚未受理数量；“已受理”不表示媒体下载成功。

主进程保存必要的批次与受理关联；临时分析索引不进入 NAS 同步，不作为永久处理历史，不依赖读取日志存续。

关闭准备提示可继续后台准备，入口保留可见的状态和停止操作；重开提示显示同一操作。应用退出必须先停止新受理，等待当前受理片段持久化、停止辅助进程，再沿用既有下载暂停/退出流程。超时需要显式提示，不因强制结束辅助进程删除作品文件。全量复制作品对象、无限并行子任务、每个请求创建一个新进程均不采用。

进程错误、任务失败与性能测量使用有界诊断：只记操作阶段、数量、耗时、阻塞时长和资源指标；不记录凭据、标题、完整目录、文件内容或原始平台响应。测量不在每个字节进度上同步写日志。

## 8. 验收与证据

### 8.1 与原问题同规模的隔离验收

- 构造 32,585 个选中作品：已失效 268、未保存 775、完整保存 31,542；含视频、图文、历史归属、同名目录和大量已完成任务。
- 使用真实临时 SQLite 和受控临时目录执行完整准备/入队路径；另保留纯分析基准，避免把测试夹具开销混入 UI 时延。
- 核对实际入队恰为 775，其他文件和读取记录不变，任务不重复、不切换来源。
- 用结构性计数证明：构建目录索引 O(N＋M)，每个批次不超过一次全库归属构建，无逐新任务全清单 JSON 解析；队列查找不退化为候选乘以历史任务数。
- 在准备期间执行心跳、状态查询、浏览、停止、正常退出；用 Electron 实际窗口验证，不只测试 Node Promise 是否完成。

### 8.2 性能预算（设计目标，非已达成承诺）

- 常规机器点击确认后约 200 ms 内呈现准备状态。
- 可控隔离负载下，主进程常规计算片段目标不超过 50 ms，事件循环延迟 p95 不超过 100 ms；超过 250 ms 的停顿必须查明阶段，不能用平均耗时掩盖。
- 停止请求约 500 ms 内被接收并反馈；当前受理片段安全收尾耗时单独报告。
- 原问题规模下准备总耗时目标较基线至少下降 80%；基线/优化需使用同一夹具、同一命令、同一机器，分别报告冷启动、热路径和峰值资源。若机器差异导致绝对门限不稳定，保留复杂度和响应性检查，并解释实际测量，不放宽到失去窗口响应。
- 热路径翻页、筛选在后台准备期间不出现明显退步；新增辅助进程空闲后能退出，不遗留无界索引或消息。
- Windows CI 避免用单个紧张的毫秒断言替代完整证据；记录多轮分位数，结构性与正确性检查必须稳定通过。

### 8.3 安全及恢复回归

- 单个/批量取消；暂停/网络失败保留续传；取消保留原有文件、其他作品及共享音频。
- 初次受理后、首次下载前外部新增/替换文件；已有 metadata、同名目录、链接、越界、根目录改变。
- 目录分析期间另一个任务完成、元数据更新、来源变化；过期和重复分析回复均不能覆盖新状态。
- 中途停止准备、部分登记失败、进程崩溃、数据库忙、磁盘满、强制退出后重启，逐项核对已受理与未受理。
- 批量移除无需旧任务不删除已完整媒体；文件状态确认与原作品状态保持独立。
- NAS 恢复与抖音下载类型、收藏顺序、新增计数、独立 NAS 目录及跨电脑删除恢复回归。

## 9. 设计决定与留给实施者的选择

已由用户确认：优先批量下载；同时检查日常浏览；采用 A＋有针对性的 B；不立即全面重构后台。

本文提出、需用户随设计审阅的决定：只读目录分析采用按需独立辅助进程；主进程保留正式写入；大库初始阈值 10,000；停止准备保留已受理任务且不自动启动；准备提示关闭后可后台继续；不要求 NAS 升级。

独立审查后补充的设计决定：同一只读快照建立索引，先结束读事务再分块回复；本批预留用覆盖层合并而不使自身反复失效；逐项失败完成后可放行成功项，整批中断则保留已受理项暂停；本批重试原失败任务与新任务使用相同的未放行限制，但不重置原文件保护基线。这些是本文提出的恢复规则，不表述为用户此前逐项确认。
