# 藏匣大资料库性能优化实施方案

目标是在数万作品、十万级文件记录下，读取、下载、备份、筛选和批量操作仍能响应界面及停止按钮。按用户确认的顺序推进：先解决读取收尾、关系查询索引、下载任务与失败补齐，再优化文件检查及界面加载，最后推进同步和搜索索引。

整理日期：2026 年 10 月 9 日。核对基线：客户端 0.3.21，NAS 服务 0.2.2，协议 2，分支 `codex/backup`，提交 `97e6263a535fb5a7a3744221d2dae51c518f2fc3`。开发进度：阶段 1 至阶段 3 已实现并通过验证，尚未发布安装包；阶段 4 至阶段 7 继续实施。下次导入时先核对实际代码、版本和工作区，再按完成记录继续，不重复已经验收的阶段。

## 诊断依据与适用范围

用户提供的遵义最新资料库有 29,666 个作品、29,666 条本地下载记录、29,666 条 NAS 下载清单和 99,730 条文件记录。下载任务同样有 29,666 条，其中 24,808 条完成、4,858 条失败。失败任务不等于所有文件都缺失，不能按任务状态直接重下作品。

“雷电将军”读取检查点已在北京时间 14:19:24 完成，共 625 条、31 页。界面仍显示 611 条，是显示进度落后于已提交进度。代码随后调用全库 `reconcile()`，每个本地作品计算目录时再次读取并解析全部下载记录，是已经确认的主要阻塞风险。

| 检查项 | 诊断结果 | 限制 |
| --- | --- | --- |
| 数据库结构快速检查 | `quick_check` 为 `ok` | 不代表所有媒体文件已经验证 |
| 8 个作品的目录计算 | 合计约 2.3 秒；每次都读取全部下载记录 | 使用本机上的只读副本，没有测遵义磁盘移动耗时 |
| 1,000 次按作品查询收藏夹 | 临时内存库约 876 毫秒；加入反向索引后约 0.8 毫秒，结果一致 | 仅代表这一查询，不能外推为整软件加速倍数 |
| 下载任务状态 | 完整任务状态编码约 5,991,932 字节 | 当前运行状态推送会携带全量任务，不能只靠前端分页减少传输 |
| 完整作品界面数据 | 约 127,196,010 字节，约 121 MiB | 诊断采用模拟文件存在结果，不包含真实磁盘开销 |
| 首次界面数据准备 | 即使不计真实文件访问，约 3.2 秒；请求约 219,410 次文件存在性检查 | 不是遵义电脑的实测启动时间 |
| 遵义日志 | 14:18:59 后本轮定时日志中断；后一次启动的会话就绪至数据准备相隔约 62 秒 | 日志没有调用栈，不能证明全部耗时来自同一个函数 |

这里只读检查上传文件，索引对照在临时内存库完成。原文件与诊断副本校验一致。旧遵义压缩包没有本地下载记录，因此此前用旧副本模拟读取，未覆盖最新库的全库整理开销。

## 实施顺序

| 阶段 | 交付内容 | 优先解决的问题 |
| --- | --- | --- |
| 1 | 定向、可停止的读取收尾和目录查找表 | 读取已经完成，但软件长时间未响应 |
| 2 | 收藏和作者反向索引、顺序查询优化 | 每次查询作品归属都扫描关系表 |
| 3 | 按条保存下载任务、任务查找表、分页状态和定向补齐 | 全量任务反复序列化、传输、扫描 |
| 4 | 文件状态摘要、后台检查和明确的未知状态 | 界面及备份频繁同步访问十万级文件 |
| 5 | 轻量列表、按需详情和局部界面更新 | 页面只显示少量作品，却加载整个资料库详细信息 |

## 阶段 1 定向整理读取结果

### 受影响作品的确定

读取页提交时记录本次更新的作品 ID、改变的归属关系及需要更新的本地信息。收尾的候选集应包含新旧关系差异、目录相关信息变化及既有未完成整理项，不只是本次新增作品。收藏夹名称或归属规则变化时，按该范围扩展候选集；不扫描无关收藏夹的所有下载目录。

区分“目录可能改变”“只需更新作品信息文件”“没有本地文件，仅更新收藏关系”。保持现有作者目录、已归档文件、未完成收藏核对、同名目录处理规则。取消收藏不能删除本地媒体，索引改变也不能改变原作品顺序和目录归属。

### 一次建立目录查找表

优先从下载记录中只提取作品 ID 和目录路径，建立“规范化路径 → 作品 ID 集合”，不要为此反复解析每个作品的完整文件清单。规范化沿用现有绝对路径和大小写处理规则。一个路径可能有多个历史引用，不能直接加唯一约束或让后读取的记录覆盖前一条。

任务内复用查找表，创建、移动、恢复、删除目录时更新对应项。变更成功后保留新旧路径的状态；回滚或失败时重读受影响项。路径查找表只用于定位及冲突判断，真正操作前仍验证根目录边界、链接和实际文件，不能取代路径安全检查。

### 收尾任务与停止

读取到末页后立即显示“读取已完成 625 条，正在整理本地作品”，将读取与整理的进度分开。持久保存待处理 ID、原因、所依据的资料修订号、当前步骤和结果。目录移动、作品信息写入和数据库更新之间保存可恢复状态，不能依赖一次性内存循环。

目录及信息文件操作按作品逐项进行；每个安全步骤结束后处理取消请求并让出界面。初始建议每 10 至 20 毫秒让出一次，这是待实测的运行预算，不是对磁盘操作时长的承诺。耗时计算和文件操作移出界面主线程；写数据库的职责保持明确，不建立多个互相竞争的写入线程。

取消只停止未执行的后续步骤，已保存的读取页和已完成的整理保留。重启后未完成整理显示为可继续，不自动恢复涉及目录移动的旧任务。再次执行前核对新修订、源目录、目标目录和文件归属，发现同名目标或差异时保留双方，不覆盖或重新下载整个库。

### 阶段 1 验收

读取该收藏夹后，只整理实际受影响且有本地文件的作品；目录查找表每轮建立一次。三万条下载记录情况下，记录整理次数及耗时，确认不存在每个作品再次全量读取下载表的行为。测试停止、强制关闭后重启、目标目录冲突、改名、收藏关系移除、作者作品被收藏及旧归档目录保留。

主要代码位置：`electron/collection-reader.mjs`、`electron/collection-reads.mjs`、`electron/store.mjs`、`electron/backup-model.mjs`。NAS 拉取、作者读取等也可能触发整理，必须检查所有调用点，不能只修一个读取入口。

## 阶段 2 关系查询索引

现有作品 ID 和下载记录 ID 已有主键索引，不重复添加。优先补以下实际查询需要的索引。

| 需求 | 建议索引或处理方式 | 依据与注意事项 |
| --- | --- | --- |
| 按作品查所属收藏夹 | `members(work_id, collection_id)` | 当前查询计划为扫描；不改变多收藏夹归属规则 |
| 按作品查作者来源 | `author_members(work_id, author_id)`、`author_scan(work_id, author_id)` | 当前反向查询扫描两个表；当前样本作者表为空，收益面向后续作者库 |
| 作者读取结果按顺序展示 | `author_scan(author_id, position)` | 当前排序需要临时排序；正式作者关系已有对应顺序索引 |
| 收藏列表的既定排序 | 候选为 `members(collection_id, (rank IS NULL), rank, work_id)` | 诊断中能消除 SQL 临时排序，但未确认总收藏成员仍有额外的归属顺序处理 |
| 按 secUid 查缓存作者 | 精确字段索引，或匹配现有 JSON 表达式的索引 | 当前仅 8 条资料，优先级较低；不是当前卡死的主要原因 |

新增索引只改变查询方式，不改变查询结果。原来依赖“查到的第一条”的归属判断，应明确原有优先规则并测试排序，避免优化后作品突然移到另一个目录。不能用作者名字替代 UID 或 secUid，同名作者及共创作者必须保持区分。

表达式索引必须与查询条件或排序中的表达式匹配。[SQLite 表达式索引规则](https://www.sqlite.org/expridx.html) 创建索引有初次构建成本，应作为一次性版本迁移执行，显示迁移状态；失败保留原数据，可重试，不能每次启动都重建。记录已完成的迁移版本，验证实际查询计划使用了索引。

验收包括新增前后结果一致、收藏和作者顺序一致、同名身份不混淆、迁移失败恢复，以及不同数据规模下的耗时。主要位置：`electron/store.mjs`、`electron/author-sources.mjs`、`electron/collection-reads.mjs`。

## 阶段 3 下载任务与失败补齐

### 任务保存和查询

把设置里的整块 `downloadJobs` JSON 迁移为按条保存的任务记录。以任务标识查询，按状态和既定顺序分页；进度变化只保存对应任务，次数和汇总也增量更新。保留原有成功历史、等待、暂停、失败、下载来源及高清图任务信息，不能为减小数据量自动删历史。

迁移在事务中完成，校验数量和字段后才切换读取来源。保留旧数据的恢复副本及迁移完成标识；新任务表为空不能被当作“尚未迁移”，否则已取消的旧任务可能再次从旧 JSON 里出现。旧程序回退和资料导入应有明确兼容策略，不让两套数据交替覆盖。

运行时维护任务 ID 查找表、各状态集合和计数。失败补齐不再对每个作品遍历整张任务列表，只查询这个作品是否有失败任务及具体缺陷。选择“补齐失败”时先显示已有失败摘要，必要时后台复查，再只处理所选缺陷；图片、视频和可选封面的状态保持分开。

### 界面状态推送

下载管理没打开时，只推送计数、暂停状态和当前正在运行的少数任务。打开后获取当前页，例如沿用 50 条；后续仅推送变化任务及计数。不要每隔 250 毫秒再次复制并发送三万条任务。正常下载、NAS 恢复和单独下载继续保持既有区分。

全选和批量操作仍支持全部符合条件的任务。使用带修订号的选择范围或稳定任务 ID 集合，不把“当前页”误当作“全部”。执行前核对范围变化，取消任务只停止队列，不删除收藏、本地已完成文件或 NAS 副本。

暂停、恢复、取消、完成等状态必须及时落盘；高频字节进度可合并更新。保留有效续传检查点，不能把任务进度条和已验证文件完成状态混为一项。

验收使用这份 29,666 条任务：未打开管理时的推送量不随历史条数线性增长；打开任一页只传页内任务；反复点击不会创建重复动作；停止和重启后取消项不复活，正常任务能继续，成功历史保留。主要位置：`electron/downloads.mjs`、`electron/flat-downloads.mjs`、`electron/defect-repair.mjs`、`electron/main.mjs`、`src/library-ui.jsx`。

## 阶段 4 文件状态摘要与后台检查

增加可按作品和文件键查询的文件状态记录，保存规范化路径、大小、修改及变更时间、最近检查时间、校验结果和错误类别。显示状态与实际文件验证分开：界面采用最近已确认摘要，并标注检查中或暂时不可确认，不在每次状态推送里同步检查全部文件。

下载、恢复、移动、删除及用户“重新检查文件”会使对应摘要失效或更新。文件监控用于提示可能变化，不能作为唯一依据；重启、磁盘离线再上线、事件丢失或目录变化时后台复查。手动删除文件后要能更新关联作品状态，不能永久依赖缓存。

检查按文件或小批进行，限制并发，可暂停及取消。磁盘无权限、不可访问和网络盘超时标为未知或受阻，不等同于删除。未知状态不能触发整库下载，也不能据此删除备份引用。

文件大小和时间可用于减少重复哈希，但不能代替要求严格内容校验的恢复、覆盖或冲突判断。真正写入、移动或删除前重新确认实际路径和文件，缓存不能绕过根目录边界或链接检查。

首次建立摘要同样是批量任务：先显示可用的记录，后台填充状态，避免把全库校验设为启动界面的前置条件。测量启动耗时、实际文件检查次数、检查取消时延及断盘后的状态，确认操作进度更新不再触发十万级同步访问。

## 阶段 5 轻量界面和局部加载

列表只获取 ID、名称、作者及共创作者摘要、类型、图片数量、标签、封面引用和本地/NAS 状态。完整视频及图片地址、目录路径、文件清单和原始标签字段在打开详情或执行操作时取回。

现有界面已有 20 条作品分页和 50 条任务分页；问题是后台仍准备和传输大量全量数据。目标是后台也按页获取列表，计数、筛选选项及成员顺序通过摘要或独立索引提供。

阅读进度、下载进度和 NAS 状态单独更新，不让进度变化触发作品列表、标签集合及成员集合重新计算。作品、成员关系、文件状态和筛选分别维护修订号；只使对应缓存失效，不用一个全局修订号迫使全部重建。读取期间不显示的封面请求可取消，当前页优先，避免请求队列持续积压。

页响应携带查询范围和修订号，异步返回时确认当前范围，防止快速翻页后旧响应覆盖新页面。保持账号收藏、作者作品、本地库、NAS 三个标签的范围与顺序；全选跨页仍可操作全部结果，不能只剩当前页。详情按需加载后，作者信息仍只手动更新，普通下载仍不自动匹配高清图。

验收测量首屏可操作时间、单次传输大小、翻页及输入响应、连续切换后的正确性。目标是加载量主要随当前页和实际变化项增长，而不是随全库详细文件记录增长。

## 阶段 6 增量同步分析

用持久变更记录保存表名、记录键、修订号及删除标记。所有写入路径都必须进入这一机制，包括直接 SQL 修改成员关系、事务回滚、NAS 应用、导入和任务恢复，不能仅监听 `put()` 而漏掉其他变动。

初始化时建立一次可靠基线；以后只重新导出受影响记录、计算它们的哈希及查询待备份文件。未变记录复用已有结果，备份线程也不应长期保留整库详细对象。内存索引只留必要键及摘要，控制长期占用。涉及隐藏作品、作者成员和媒体引用的变化要连带更新相关项。

变更记录与作品数据在同一事务里提交。NAS 确认后只清除对应修订以前的变更；上传时又发生编辑的记录继续待备份，不能因旧回执而丢失。保留库标识、写入租约、冲突保护、幂等提交、待确认回执和断线后本地保存规则。

发生无法证明基线可靠、来源库变化或变更日志缺口时，允许后台完整比对，并说明原因；不能为了速度跳过必要核对。普通轮询只查询轻量状态，不在每次心跳里重新检查全部本地文件。

这一步最后实施，验收重点是新增、编辑、删除、重启、回执丢失和同步中再次编辑均不漏备份。普通记录编辑的处理量应主要与变化数量有关，而不是每次重新解析数百 MB 数据。

## 阶段 7 搜索与筛选索引

建立作者身份、共创作者身份、标签、我的标签和下载状态到作品 ID 集合的反向索引，筛选时取并集或交集，再按原收藏或作者顺序展示。只因对应字段改变而更新，不因进度条或音量改变而重新统计全库。

搜索文本预先规范化并缓存，避免每次输入都重新拼接名称、描述、作者身份及标签。全文索引作为后续选项；中文短词、部分词、大小写和当前包含匹配语义须验证，不能擅自改变搜索结果。SQLite FTS5 的 trigram 全文查询对不足三个字符的子串有明确限制，因此短词需要兼容策略。[SQLite FTS5 说明](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)

较慢的搜索放到后台，快速输入时取消或丢弃旧查询结果，界面先保持可操作。搜索计数与选中范围绑定相同修订；索引可从正式资料重建，不能成为无法恢复的唯一数据来源。

验收包括同名作者、共创作者、中文一至两字、标签组合、跨页全选、NAS 已删除作品及归档作品范围。优化前后命中和顺序一致，不能用速度换取漏检。

## 统一性能与正确性验收

每阶段保留真实数据规模基线和脱敏测试样本，分别记录查询次数、JSON 读取与编码字节、文件检查次数、内存峰值、事件循环最长及分位延迟、界面响应和取消时延。测试实际安装包，而不只测函数。

初步目标是在常规大任务中，进度仍持续更新，点击停止后尽快显示“正在停止”，在当前安全操作结束后停止后续步骤。不能给无法中断的底层磁盘操作承诺绝对毫秒期限。没有未响应提示也不等于达标，需要与三万条资料的旧版实测比较。

全选取消、失败重试、读取中断、NAS 断联、磁盘离线、重启和并发点击都需覆盖。旧资料不能因缓存或索引迁移被清空；错误提示需明确区分未知状态与缺失，已有文件和备份保护规则保持不变。

新增索引、摘要及查找表都是可重建的辅助数据。迁移只运行一次，失败保留原资料；保留事务与恢复检查点。不要通过降低 SQLite 的持久化强度来掩盖耗时，也不要在用户资料上直接执行破坏性性能测试。
