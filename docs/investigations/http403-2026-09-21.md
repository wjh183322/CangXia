# 两台电脑收藏读取差异：证据与结论

## 已确认的事实

- 用户反馈：一台电脑的网页和软件均能读取，另一台电脑专用浏览器可读而软件返回 HTTP 403。两台电脑使用不同网络。
- 独立诊断报告记录：问题电脑的 Electron 44.3.0 直接请求返回 403；从同一份专用 Chrome 153 会话出发，在网页内执行请求返回 HTTP 200、业务代码 0、10 个作品，并有下一页。
- 报告在两条路径都没有观察到已知签名字段。这不是“没有任何签名或令牌”的证明，因为检查只覆盖指定 URL 参数名，不包含所有网页逻辑、请求头和服务器内部校验。
- 生产代码检查未发现按开发电脑用户名、电脑名或机器 ID 放行读取的逻辑。账号绑定用于防止不同账号的资料混在一起，不是开发机授权。

## 目前能下的结论

差异已定位到登录之后的读取路径：旧二维码登录使用 Electron 会话直接发送请求；诊断成功的方式是在系统 Chrome 已加载的抖音页面中发送请求。扫码成功不等于后续所有请求方式都会被服务器接受。

浏览器网页执行环境与直接网络调用不是同一条路径。网页自身的请求处理、实际携带的状态和请求上下文等可能不同；两台电脑又使用不同网络，因此网络出口或平台对环境的判断也尚未排除。现有报告没有提供服务器拒绝请求的具体内部规则，不能认定唯一原因是签名、IP、某个请求头或开发机身份。

## 0.2.6 的处理

各登录入口统一交接到系统浏览器的后台页面并核对账号，消除已确认的读取实现差异。使用浏览器本身的网页执行环境，不伪造签名、不关闭安全校验、不在限流后切换方式反复请求。

后台实现采用 Chrome DevTools Protocol 的隐藏页面能力；该页面不在普通标签栏中，生命周期受协议会话限制。[Target.createTarget 官方定义](https://chromedevtools.github.io/devtools-protocol/tot/Target/#method-createTarget)

测试发现后台冷启动的初始页面注册时机问题，Chromium 官方也记录过此竞态。实现只对本地浏览器页面创建做有限等待，必要时使用短暂的最小化空白引导页面，随后立即删除；这不是重试被平台拒绝的收藏请求。[Chromium 启动竞态记录](https://chromium.googlesource.com/chromium/src/third_party/+/cb8a25f1f138378f6e561c4bf18dd0bc1c63faed)

## 若要进一步区分网络与电脑因素

使用同一版本诊断工具、同一账号，在两台电脑连接同一个网络并保持代理设置一致后，各执行一次小范围对比。再仅改变网络，观察结果是否随网络变化。保存 HTTP 状态、数量和环境版本即可，无需提供 Cookie 或验证码。

若失败跟随网络改变，支持网络环境相关；若在相同网络下仍只有一台失败，需继续比较浏览器版本、代理配置、会话和请求上下文。即使如此，也不能在缺少服务器依据时声称已知道平台内部拒绝规则。
