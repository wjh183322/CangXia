# 下载、问题面板与取消收藏研究

日期：2026-10-20。状态：用户已确认设计，进入实施计划审阅；未修改产品代码。基线：0.3.34，`f3b79e9a12ee4f0ce07a2944e2709e6a5e7fe5b9`。

## 1. 请求与边界

| 项目 | 用户要求 | 建议范围 |
|---|---|---|
| 下载详情 | 正在下载时点击标题打开作品详情 | 复用按精确作品 ID 的本地详情，下载继续；返回保留下载列表状态 |
| 检查详情 | 检查与补齐中点击标题打开作品详情 | 返回保留筛选、页码、滚动与选择；打开抖音仍是独立按钮 |
| 大小排序 | 本地媒体库按大小排列 | 收藏顺序、大小降序、大小升序；使用已保存大小索引，排序后再分页 |
| 手动检查 | 打开检查面板不自动扫描全部作品 | 默认加载已保存的问题总览，手动检查全部或选中项 |
| 问题保留 | 核验 74 条或补齐 9 条不使原有 204 条失效记录消失 | 全局问题集合与本轮任务结果分开，按项更新且持久保存 |
| 失败诊断 | 可访问的视频补齐仍失败 | 已定位并隔离复现一种与截图相同的状态确认失败，实际样本仍需清单核对 |
| 取消抖音收藏 | 研究是否可从藏匣操作 | 仅研究，不执行账号操作，不与本地/NAS 删除捆绑 |

NAS 跨设备删除、找回和恢复的正式设计另见 `docs/superpowers/specs/2026-10-20-cross-device-deletion-and-recovery-design.md`。

## 2. 当前实现中的问题

- `src/main.jsx` 的 `scanDefects()` 在打开面板时立即调用 `inspectDefects()`；服务端随之全量扫描。尚无“只加载已保存总览”的入口。
- `electron/defect-repair.mjs` 的 `scanItems`、`scanToken` 是内存数据；任务数据库只保存一个当前任务，新核验或补齐会替换它。
- `src/defect-repair-ui.jsx` 在任务运行时自动切到“补齐结果”；该页按本轮选中项目统计，而不是全部问题。因此核验 74 条后看不到本轮未选中的 204 条，处理 9 条后也只显示这 9 条。
- 0.3.34 已纠正本轮进度混入历史失效、以及重扫后忽略保存的未知源状态，但没有实现持久问题总览、手动打开、任务历史或保持当前标签。
- 当前处理状态同时混合源作品状态与下载状态。可访问与下载失败实际上可以同时成立，单一标签容易造成误解。
- 本地轻量视图已有 `localBytes`，由文件状态及资产清单汇总；当前过滤器和搜索索引未提供按大小排序。
- 普通下载管理已有按 ID 打开失败作品详情的回调；活动任务标题的可点击范围需要扩展。
- 浏览器请求封装当前只允许读取接口，没有已实现的取消收藏写入渠道。

## 3. 文件确认失败：已复现的路径

用户样本：作品 `7682358658709391717`。用户确认网页可播放，并提供本机目录截图：视频约 2,276 KB、单图约 162 KB、作品信息 JSON 约 3 KB，另有 0 KB 的 `作品信息.json.part`。不能据此推断所有 9 条作品状态相同，也不能仅凭存在文件就证明媒体完整。

错误原文为“已保存内容保留，文件确认暂未完成：已保存文件的当前状态未通过确认”。该文字来自 `electron/downloads.mjs` 的下载后确认阶段，不是抖音的作品不存在提示。

已经用隔离合成库验证：

1. 三个必需文件存在、大小与清单一致，但 `downloads.state` 为 `partial`。
2. `inspectWorkFiles()` 返回 `complete`；`saveFromDouyin()` 提前返回“文件完整，无需补齐”，没有更新保存清单状态。
3. `FileStates.confirmWritten()` 遇到清单不是 `complete` 直接返回 false，下载任务于是失败。
4. 重试两次均出现与截图完全相同的错误，没有发起任何平台或媒体请求。
5. 对照实验只把合成清单状态改为 `complete`，同样的文件立即通过确认，所有文件哈希保持一致。
6. 对照时 0 KB `.part` 仍在，说明这个临时残留不是该失败路径的必要触发因素。它需要进一步核实来源，不能直接作为删除或重下载的理由。

诊断脚本：`.test-output/diagnose-file-confirm-20261020.mjs`。结果：`.test-output/file-confirm-diagnosis-1792497629710/report.json`。这些是合成样本，不是用户实际下载文件的检查结果。

用户随后提供了实际 `作品信息.json`：作品 ID 与样本一致，`remoteState` 为 `available`，`assets` 仅登记 `cover / 单图.jpg / 165039`，没有 `video` 条目。`savedAt` 为 `2026-10-12T17:44:43.698Z`，`checkedAt` 为 `2026-10-19T18:29:26.132Z`。元数据文件不列出自身的 metadata 资产是正常行为，不能据此判缺失。

这与截图中存在 `视频.mp4` 形成新的核对点，但该 JSON 可能是旧快照，不包含当前数据库的 `downloads.state`、完整下载清单或视频归属证据。因此，不能断言用户实际问题必然等同于合成库的 partial 状态循环，也不能仅凭文件名把视频认领为完整。实施时同时覆盖“完整已登记文件＋部分状态”与“视频存在但未登记／元数据过旧”两条路径；保留原文件。必要时导出仅该作品的脱敏诊断，不要求上传整库。

## 4. 建议的故障修复

文件确认与平台可访问性分开：平台可访问只说明取得相应详情和资源，文件成功需要经过本机确认。

- 已存在文件按当前必需资产与清单核实；全部通过时，原子更新这条保存清单为完成，再更新文件状态缓存，不反复下载已验证文件。
- 提交前确认校验期间保存清单与目录归属没有变化；变化时重新确认当前条目，有限次重试后保留为“待确认”，不误报完成。
- 缺损资产只补缺损项；目录不可用、符号链接、权限错误和清单并发变更分别给出具体原因。
- 缺少的清单、清单仍部分完成、哪一个文件缺失或大小不符、清单在确认期间更新要分别可诊断，不能全部压成同一句“下载失败”。
- 已下载字节和正确文件保留。检查、停止、重试不会把原有文件清空。

验收必须覆盖完整文件配部分清单、真实缺失、大小不符、清单变更、不可用目录、停止和重启；不能以简单取消确认来让任务变绿。

## 5. 问题总览与本轮结果

建议将面板的两个标签明确为“问题总览”和“本轮结果”。默认打开问题总览，不因开始任务而自动切换；上方显示本轮进度，列表仍可查看全部已知问题。

问题总览在本机 SQLite 中按作品 ID 持久保存最近已确认的问题、时间及诊断摘要，与任何单次任务的选中范围无关。采用按项更新：

- 核验 74 条只更新这 74 条的源状态，其余 204 条失效记录继续存在。
- 补齐 9 条只更新这 9 条的文件、任务结果，不替换整个总览。
- 只有对某项完成检查并确认正常、或明确移除该项后，才将对应问题解决；未检查、停止后未处理的记录不被当作正常而清除。
- 重开、重启、切标签和新建任务不会清空总览。
- 本轮结果只展示相应任务处理的项目，明确范围与数量；读取旧结果不会改写当前总览。

拆开“文件/处理状态”和“原作品状态”筛选。一个作品可同时是“原作品可访问”和“下载失败”，保留两个事实；不以可访问替换下载失败，也不以一次补齐失败清除已失效状态。总作品数去重，各类问题数量允许重叠，界面说明。

面板打开只读取保存的总览与最近任务摘要，不进行磁盘全量扫描或平台核验。提供手动“检查全部”“检查选中”以及独立“核验原作品状态”。已有后台文件监测机制不因打开面板额外加跑一轮。下载结束等变化只更新涉及作品。

筛选、页码、滚动和选择在查看作品详情返回时保留；任务或数据变化导致选择失效时清楚提示，不悄悄扩展选择范围。

总览存最近状态，不保存平台完整响应；任务摘要及必要差异保留有限历史。使用索引、分页、筛选快照及批处理，不把三万条问题明细一次发给界面。日志清理不清空仍未解决的问题。

## 6. 标题详情和大小排序

普通下载管理的活动任务以及检查面板的标题都按精确作品 ID 打开本地作品详情。此操作不暂停队列、不刷新作者、不发起原作品核验。关闭详情返回原列表位置。未找到记录时保留任务并说明原因，不通过同名搜索猜测替代作品。

本地媒体库新增“收藏顺序 / 本机文件大小从大到小 / 从小到大”。默认仍为收藏顺序，先筛选再排序再分页，相同大小按原顺序稳定排列，未知大小置后并标识。

大小使用已保存的本机文件索引，不因排序遍历磁盘；浏览缓存不计入正式作品大小。共享配乐单独标识，不把相同共享音频重复计成可释放空间。全选、详情位置与翻页基于当前排序；收藏来源的原读取顺序不被改写。

## 7. 取消抖音收藏的研究边界

截至 2026-10-20，查阅了抖音开放平台移动/网站应用的公开 OpenAPI 列表，没有找到足以确认可直接用于本功能的“取消作品收藏”接口文档。此结论只表示本次公开文档检索没有确认支持，不证明平台内部没有相关接口。

来源：<https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/list>。该文档页面的“收藏/我的收藏”是文档站点自身操作，不能当成抖音作品收藏 API。

可进一步研究的路线是当前用户已登录的抖音正常网页操作：确认作品 ID 和当前账号，观察可用的收藏控件与真实结果。当前未执行任何取消，也未验证其稳定性，不能承诺失效作品或批量作品均可操作。

若后续单独实施，必须：

- 使用明确的“取消抖音收藏”入口，展示所选作品及账号；不能由删除本机/NAS 读取记录、检查失败或后台同步自动触发。
- 将账号写入操作与当前只读 API 通道分开，使用平台正常登录与交互，不猜测接口、不构造签名、不绕过验证。
- 对已失效作品、已取消收藏、未登录、验证码、访问限制、停止和重复点击分别验证。
- 成功要通过对应账号、作品及收藏状态回读确认，不能把 HTTP 成功或 `status_code:0` 单独当作取消成功。
- 默认保留藏匣本地与 NAS 文件、历史读取记录；本地/NAS 清理另选，不隐式联动。
- 如无法取得可验证的正常操作方式，只提供打开原作品或收藏页协助用户处理，不宣称已完成平台取消。

本次只完成公开文档与本地代码研究，没有修改抖音账号收藏。

## 8. 已确认顺序与实施计划

1. 优先确认并修复下载后文件确认循环，补具体原因和局部状态修复，保留已有文件。
2. 完成标题详情、大小排序以及手动打开/持久问题总览，保持已知问题与本轮任务分离。
3. NAS 跨设备删除恢复设计已获确认，另行生成协议与客户端分阶段实施计划。
4. 取消收藏维持独立研究；真实操作探针和后续实现须另行明确授权与验证范围。

先前提供的 `status_audit_self_see` 空文字过滤响应仍是待补充识别的独立案例，应保留在后续原作品状态修复清单，不能因本研究而遗忘或视为已经完成。

本机实施计划：`docs/superpowers/plans/2026-10-20-local-download-and-problem-overview.md`。取消收藏仍仅研究；设计确认不代表授权执行抖音账号写入。
