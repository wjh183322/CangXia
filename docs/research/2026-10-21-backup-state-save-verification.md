## 修复行为

原 0.3.36 Windows CI 在初始化同步时对 backup-state.json.tmp 替换 backup-state.json 返回 EPERM，旧代码单次同步替换失败即可导致 NAS 状态不可用。该错误是电脑端同步状态保存失败，不是用户真实 NAS 媒体损坏的证据。

保存现采用异步串行快照、独立临时文件、写入及刷新后替换；EPERM/EACCES/EBUSY 默认最多约 3 秒重试，等待时让出线程。失败不删除旧状态，明确提示本机状态保存失败。状态文件格式、库 ID 与 NAS 0.2.4 服务协议不变。NAS 服务及 shared 源码树与已发布 0.2.4 相同。

关键 NAS 提交须等待恢复凭据保存；等待期间停止不会继续提交。NAS 已完成但本机确认保存失败时，实际重开 profile 可以按原 requestId 回读回执，不产生重复提交。范围删除回执保存失败则保留本机剩余步骤，明确重试不重复删除 NAS。连续快照不因后续对象修改而改变，退出等待已请求保存。

较早开始的状态分析在同步完成后返回时，必须重核对库和基线版本；数据变化就重新分析，保存后再次核对，不用旧 dirty 状态覆盖已同步结果。

## 专项验证范围

1. 真实 Windows CreateFileW 句柄允许读写、拒绝删除共享，实证 rename 被拒；解除句柄后替换成功，期间有事件循环心跳。不能据此断定原云端占用者为杀毒软件或特定程序。
2. 持续拒绝、磁盘错误保留旧 JSON；短暂失败不触发 NAS 不可用或暂停无关任务。
3. 提交前失败没有记录提交，恢复后提交一次；提交后确认保存失败，实际关闭重开后不重复提交。
4. 已获范围删除回执后保存失败保留本机文件，明确重试只做剩余步骤；B 保留账号/作者来源并显示待处理。
5. 等待保存时停止、不向 NAS 继续提交；并发本机编辑保留，下一轮正确同步。
6. 封面、视频和共享 WAV 经保存失败重试后核对清单、NAS 对象与确认进度，音频字节一致。
7. 受控时序复现旧分析晚返回、工作线程等待期间已刷新后晚返回两条路径，均先 RED，再修复为 GREEN。
