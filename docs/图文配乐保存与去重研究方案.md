# 藏匣图文配乐保存与去重研究方案

目标是在藏匣浏览图文时播放作品实际使用的配乐，并让多个作品共用相同音频，避免重复下载和存储。建议采用“作品配乐信息 + 共享音频文件 + 独立播放控制”的方式，不把图片和音乐合成视频。

更新日期：2026 年 10 月 11 日。原稿整理于 10 月 9 日；本次核对客户端 0.3.27，NAS 服务 0.2.2，协议 2，分支 `codex/backup`，提交 `10fb4a0f7ebc0f1dd29997304b8e61c24a063547`。已进行小范围真实音频实验并继续修订方案，没有修改正式程序的解析、下载、播放、数据库或 NAS 服务。实验进展与未覆盖项见同目录《图文配乐真实样本实验报告-2026-10-11》，不能把研究脚本视为产品功能已经上线。

## 快速理解与这次修改

这里的“配乐”指声音文件；作品文案仍是少量文字，不能用文案大小代替音频大小估算。

推荐默认采用“读取只存音乐信息，打开图文后按需播放，试听缓存有上限；只有明确保存才永久留在本机”。去重负责避免重复保存同一音频，容量限制负责控制很多不同音频的总空间，两者都需要。

| 场景 | 配乐处理 | 是否大量占本机空间 |
| --- | --- | --- |
| 读取几万条图文 | 尽可能保存音乐 ID、标题和作品绑定，不下载整库音频 | 主要增加少量元数据，仍需实测数据库索引开销 |
| 普通下载图文图片 | 默认保存图片与已有配乐信息，不自动永久下载所有配乐 | 不因原有“全选下载”变成额外下载几万首 |
| 打开图文听配乐 | 已保存文件或有效试听缓存优先，缺失时按需取；音频不阻塞图片显示 | 可淘汰的试听缓存，建议上限 256 MiB |
| 希望离线有声音 | 勾选“保存配乐到本机”或手动补齐，按确切音源共享文件 | 属于正式媒体，会增长，不能自动清理 |
| 希望长期留配乐但本机少占空间 | 后续提供明确的“仅保存配乐到 NAS”批量任务；少量暂存，确认后释放 | 不整库落地；这是待兼容验证的后续能力 |
| 第二台电脑同步 NAS 记录 | 只同步绑定和对象引用，听到哪条再取哪条 | 不自动把全部 NAS 配乐恢复到本机 |
| 清理试听缓存 | 删可淘汰音频，不删作品、音乐关系、正式音频或 NAS 对象 | 下次有网络可重新取，离线时未缓存的不能播放 |

旧稿的“下载图文时默认同时保存配乐”改为建议默认关闭，避免用户已有两万多条图片下载任务被额外扩张。浏览时默认按需缓存；永久保存和 NAS 保存均需明确选择。参数是方案建议，尚未生效。

保存到本机和仅保存 NAS 是两个独立入口，共用下载、验证与去重任务。保存到本机后，开启现有自动备份时仍会备份到 NAS；仅保存 NAS 则不要求永久本地副本。可以同时满足两种保存意图，不能把它们做成必须二选一的模式，也不能给两个入口各下载一次同一音源。

## 首轮真实实验后的优化结论

已实时取得 12 条图文的接口信息并完整解码全部音频，其中 11 条有音乐直接地址，1 条音乐地址为空但图文 `video.play_addr` 返回纯音频。7 条进一步确认接口取得的文件与官方网页实际请求文件字节完全相同。实测材料及局限见 [真实样本实验报告](图文配乐真实样本实验报告-2026-10-11.md)。

本轮支持直接获取配乐，不需要默认下载视频或做全视频匹配。应同时保存图文专用的 `image_album_music_info`：本轮起止字段按毫秒与实测播放相符，音乐时长字段按秒返回；不同字段不能混用单位。音乐时长可为整数近似，不能拿它截断实际文件。

后续边界实验已把完整解码累计扩展到 16 条图文、网页文件字节对照累计 11 条；额外 21 次详情请求取得 20 条对应作品。发现 -1 片段、false 音乐标记但实际可播，以及约 310 秒的备用音轨。还验证了特定 CDN 忽略错误 If-Range、当前 NAS 服务的引用与旧客户端恢复障碍。最新准备状态见 [边界验证与实施准备](图文配乐边界验证与实施准备-2026-10-11.md)，不能仅按首轮报告判断验证已全部完成。

| 信息 | 保存及使用规则 | 本轮证据／限制 |
| --- | --- | --- |
| 音乐条目 ID、名称 | 作为条目及展示信息，ID 精确字符串 | 两条同 ID 的图文确实共用同一音频，但不能据此保证所有同 ID 的版本都一样 |
| 直接音源候选 | 原始格式取得并验证，登记来源字段和内容版本 | 样本出现 MP3 与 AAC/M4A；不统一改名成 MP3 |
| 图文 `video.play_addr` | 仅作为图文的受验证候选，不按字段名判断媒体类型 | 一条取得纯 AAC/M4A；必须验证无视频轨，不能泛化到普通视频 |
| 图文 `begin_time`、`end_time` | 保留原值与已验证单位；保存规范化范围及确认状态 | 全部起点为 0；长音频实测网页在声明片段末尾附近循环，非零起点仍未覆盖 |
| 图文 `volume` | 保留作品原始参数，全局音量单独处理 | 本轮有 100／110；换算与混音规则尚未证实，不能直接当 HTML 音量 |
| 音源实际时长和完整性 | 由文件解析、解码或可靠播放验证得出 | 不用音乐整数时长、图文结束字段或 HTTP 200 单独证明完整 |
| 获取状态与验证级别 | 区分已确认音源、片段待确认、仅音源试听、暂未取得、明确无音乐 | 地址缺失不等于没有配乐，不能把未知覆盖成无音乐 |

保存采用“原音源对象＋作品播放参数”，第一版不为每条图文物理裁剪并另存一份。两条同源、不同片段可共用对象，播放时重新应用各自参数。接近文件边界的声明差异保留原值并验证后约束到可播范围；明显越界、负值或单位未知时，不猜片段，不默默改成整曲。

第一版读取仍仅解析列表已经返回的小量字段，不做每作品网页音频对照；本次网页请求和解码属于研究验收。缺少音源时才在单条播放、保存或手动补齐阶段请求详情。内容去重仍按可靠资源版本及完整文件 SHA256，波形相关仅作实验，不用于自动合并。

## 现有程序与获取配乐的依据

当前 `electron/model.mjs` 的 `parseWork` 处理作者、图片、视频及封面，没有保存音乐对象；`electron/downloads.mjs` 的图文下载目标只有图片，作品信息文件也不包含配乐；`src/library-ui.jsx` 的浏览器只显示图片和视频。因此，现有记录里没有配乐，并不代表原作品没有音乐。

F2 项目的抖音解析代码读取作品详情中的音乐 ID、标题、作者、时长及 `music.play_url.url_list`，其下载模块直接下载该音频，并把图文图片作为另一组资源处理。这支持“直接获取配乐地址”的技术路线，但不是对藏匣当前登录会话下每条作品都能获取的保证。[F2 解析源码](https://github.com/Johnserf-Seed/f2/blob/main/f2/apps/douyin/filter.py)、[F2 下载源码](https://github.com/Johnserf-Seed/f2/blob/main/f2/apps/douyin/dl.py)

已有真实作者列表响应含音乐对象，实时作品详情又验证了直接音源和图文起止字段。仍需补充登录态收藏列表、非零起点、变速、混音和手机端音量对照；不能把公开网页少量样本写成所有接口都会提供的固定平台规则。

## 保存作品实际配乐

优先级建议如下：若平台提供已确认与作品播放一致的音轨，直接保存；若提供可复用音源及明确的作品剪辑信息，保存共享音源，并单独保存作品起止时间等参数；若只得到音乐条目音源而无法确认作品剪辑，则标为“配乐音源已保存，作品片段待确认”。不能用同名歌曲替换，也不能默认一首完整歌曲等同于原作品听到的声音。

音乐条目可能表示原声或音乐资源，不一定是商业歌曲名。标题、作者名仅用于展示；不存在音乐、暂未提供、地址过期、获取失败、平台标记不可用应分开表示。未返回音乐字段属于未知，不覆盖已有成功配乐信息。

新读取的图文随作品信息保存音乐元数据，不在读取时下载所有音频。旧作品提供单个或勾选批量的“补齐图文配乐”，只更新所选缺失项，不要求重新读取几万条收藏。已有图片完整状态保持独立，不能升级后把全部旧图文变成下载失败。

## 判断是否为同一音频

“同一首歌”“同一平台音乐条目”和“相同可播放音频文件”是三个层次。为了保持原作品声音，第一版按实际音源版本和文件内容去重。

| 判断依据 | 用途与限制 |
| --- | --- |
| 音乐 ID | 查找已有音乐条目；使用精确字符串，不能经过可能丢精度的数字转换；单独作为 ID 不能证明所有作品音轨相同 |
| 已验证的音源资源标识及版本 | 下载前查找可复用对象、合并并发任务；需从实际响应确认标识含义 |
| 音频文件 SHA256 | 文件内容完全相同可共用一个对象，即使音乐 ID 不同；通常要在首次取得文件后才能计算 |
| 作品片段起止时间、变速、混音信息 | 区分作品使用方式；同一完整音源的不同起止时间可共用文件，通过播放参数区分 |
| 标准化解码后音频比较 | 后续可用于相同声音但不同封装的核对；有计算成本，不能因此覆盖原始文件 |
| 歌名、作者名、URL 文本 | 只能辅助查找，不能单独作为自动合并依据 |

具体复用流程：先检查作品已有绑定和有效文件，再查询音乐条目与已确认的资源版本绑定；匹配时复用文件，正在下载时加入同一任务。没有可靠匹配才下载，下载完成后以 SHA256 登记共享对象；发现相同哈希则关联已有文件，释放新产生的重复临时文件。临时地址变动不能自动生成新的音乐条目，音源内容发生变化也不能覆盖旧版本。

不能任意删掉 URL 的所有查询参数来判断相同资源：其中可能包含转码、版本或资源选择参数。仅忽略经样本确认属于临时授权且不影响内容的参数。可用时结合响应的版本验证信息；验证不足则保留不同版本，不能为了减少下载误播其他声音。

第一版能避免已知同一音源在多个作品里反复下载，并保证相同文件只存一份。不同音乐 ID、不同未知地址第一次下载后才发现内容相同，仍可能产生一次重复网络传输；不能承诺完全消除所有未知来源的重复下载。

音频指纹适合发现相似录音，不能证明剪辑、速度、音量和混音完全相同，不作为第一版自动合并条件。FFmpeg 支持对解码音频计算哈希，可作为后续严格内容比较的工具；解码格式、采样率和通道布局等条件需要固定。[FFmpeg 哈希文档](https://ffmpeg.org/ffmpeg-formats.html#hash)

## 本地共享存储和数据模型

明确“保存到本机”的音频属于正式媒体，放在用户选择的下载根目录下的共享配乐目录；试听音频属于可淘汰缓存，放在资料目录的独立音频缓存区。两类可复用相同内容对象，但不能把试听关联当成永久保存承诺。

```text
下载根目录/
  配乐文件/
    ab/
      <SHA256>.<实际格式扩展名>
  收藏夹或作者目录/
    作品目录/
      图片文件
      作品信息.json
```

路径由程序根据固定规则生成。作品信息通过对象标识和受约束的根目录相对引用找到配乐，不保存供另一台电脑直接使用的绝对路径；不能接受作品字段提供任意路径。下载根目录变化或资料导入时重建关联。

建议区分以下记录：音乐条目保存平台音乐 ID、标题和作者；音源版本保存资源标识与对应内容对象；内容对象保存 SHA256、大小、实际格式、时长及本地状态；作品配乐关系保存作品 ID、音源版本、片段参数和获取状态。保存文件的存在性、完整性和引用关系需要实际校验，不能只依赖“曾下载成功”标记。

所有 ID 均精确保留。原始文件按实际格式保存，不统一改扩展名成 MP3，也不默认转码。音频嗅探、大小、时长和播放解码验证用于拒绝错误页面及损坏文件。长音频采用流式文件播放，不把整首音频和整库对象放进主进程大字符串。

第一版不在每个作品目录复制一份相同音乐。若以后增加“导出独立作品包”，导出时可以附带一份配乐；用户主动导出产生的副本与资料库内部去重分开统计。

## 下载与补齐入口

新下载图文时提供“同时永久保存配乐到本机”，建议默认关闭，只作用于本次选择的作品，并在确认页展示独立的配乐预计空间及复用情况。升级后的既有图片下载队列不自动追加配乐任务。默认值尚未由用户确认。用户没有要求保存音频时，图片完整就是图片完整，不显示整个作品下载失败；要求保存但音频失败时显示“图片已保存，配乐待补齐”，只重试音频，不重下图片。

本地库勾选图文后可“补齐配乐”，作品详情也提供同一入口，区分“更新配乐信息”和“保存缺失配乐到本机”。批量确认显示作品数量、已知可复用音源数和待获取项；元数据或长度不足时显示未知项，不能伪造准确音乐数量及大小。浏览按需播放与缓存，不自动升级为永久保存；取消永久保存任务不删除已经下载的图片和记录。

配乐下载按音源去合并任务，并受全局媒体下载并发约束，不能在现有 6 个作品任务之外额外无限并发。多个作品共用一个下载任务时，取消一个作品只解除它的等待关系；只有没有其他等待者时才停止共享下载。暂存文件和续传检查点与内容对象分开记录。

沿用现有来源规则：日常收藏和作者作品下载优先抖音，获取不到且 NAS 有对应版本才回退；NAS 页的恢复明确走 NAS。本机已有有效音频先复用。备份仅在空闲启动，配乐获取失败不能中断收藏读取，也不能触发大量可见浏览器窗口或无限登录重试。

## 像抖音一样浏览和播放图文

播放器按作品拥有一条配乐播放会话。同一作品左右翻图片时音乐连续播放，不重置；切换到另一作品先停止旧配乐，再按新作品自己的播放片段开始。不同作品恰好共用音频文件，也不自动沿用上个作品的播放位置。

复用顶部现有全局音量及静音设置，增加配乐名称、播放暂停和音频状态。默认音量目前为 0，应让用户明确取消静音；播放是否按作品片段循环需要核对实际样本，先按已取得的片段循环，不自行推断起止位置。自动翻图片是另一个体验开关，不能用猜测的翻页间隔冒充抖音实际时间轴。

关闭浏览器、切换作品、打开覆盖的弹窗时暂停或停止，具体返回策略保持一致；只能有一个前台声音会话，视频与配乐互斥，避免详情和浏览器各播放一份。异步请求返回时核对当前作品，防止快速切换后播放错音频。

浏览器可能限制有声自动播放。首次由用户点击开始或取消静音时启动；若播放被拒绝，显示播放按钮而不是假装已播放。图片可立即展示，音频加载不阻塞翻页。媒体控件可处理暂停、静音及循环，但不会自动解决作品与音源对应关系。[MDN 自动播放说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

## 本次细化：试听缓存、空间预算和播放来源

### 先明确三种保存意图

试听、永久本地保存和永久 NAS 保存是三种独立意图，可同时存在；不能仅用“有配乐关系”来判断音频必须永久留在本机。

| 状态 | 文件放在哪里 | 自动清理 | 空闲备份 |
| --- | --- | --- | --- |
| 仅有配乐信息 | 数据库中的音乐条目和作品绑定，没有音频文件 | 不因清缓存删除必要绑定 | 音频元数据在兼容支持后可随记录同步，不触发整库音频下载 |
| 临时试听 | 本机受限音频缓存，或有界的流式缓冲 | 无正在播放／任务依赖时可淘汰 | 默认不上传音频；听过不等于要求备份 |
| 永久本地保存 | 下载根目录的共享配乐对象 | 不按缓存预算删除 | 用户原有备份开启时，像正式图片一样备份现有音频 |
| 已明确要求仅保存 NAS | 小批取得音频，待 NAS 对象及作品引用确认后释放本机暂存 | 未确认不能删，确认后不需要永久本地副本 | 只处理用户选中的任务，不自动扩展到整库 |

“仅保存 NAS”不是拿已经属于正式本地媒体的音频随意删除：若对象还有其他作品的本地保存引用，或用户同时要求本地保存，继续保留本地正式文件。听过的音频若在缓存中完整有效，用户再点保存可复用，不重下；跨磁盘移动需要验证复制、原子登记和失败回滚，播放期间不直接移动正在读的文件。

### 容量控制不只靠音乐去重

与封面共用资源记账，建议浏览缓存总额 1 GiB，其中封面 768 MiB、配乐 256 MiB；另有合计 256 MiB 备份准备预算。配乐完整缓存、片段缓存、未完成试听文件和预留都计入音频额度；仅保存 NAS 的待确认文件计入备份准备额度，不同时把同一物理文件算两次。

正式本地配乐单独显示占用，不受试听额度淘汰。设置页展示“试听缓存占用／可清理／当前使用”“永久保存配乐占用”“待确认备份占用”和“关联作品数／独立音频数”，统计实际文件字节，不按作品数乘平均值冒充真实大小。

以下只是空间估算，不是对真实配乐平均大小的测量：

| 假设 | 仅音频约占空间 |
| --- | --- |
| 三万图文，各有不同的 2 MB 音频 | 60 GB，约 55.9 GiB |
| 三万图文，最终只有五千个不同的 2 MB 音频 | 10 GB，约 9.3 GiB |
| 只试听且受 256 MiB 缓存约束 | 可管理的音频缓存不随整库作品数一直增长，另有当前播放缓冲和必要索引 |
| 三万条作品绑定，每条按 1 KiB 举例 | 约 29.3 MiB 文字数据；数据库页、索引、音乐版本表另计，需实际测试 |

不默认重编码降音质来解决容量，不无条件缓存整首歌，也不承诺“几万首不同配乐全部离线又几乎不占本地空间”。全库离线、本机限额和源消失后永久可用不能同时无成本保证；让用户在试听、本地保存和 NAS 保存之间明确选择。

### 流式播放是网络优化，不等于零缓存

优先使用有效的正式本地文件，其次完整试听缓存或可用片段；日常在线浏览优先抖音，源确实不可用且 NAS 有对应音轨版本时回退。NAS 页面明确恢复或试听 NAS 对象时直接使用 NAS。不要在抖音断联时无限重试，也不要绕过现有 NAS 只读规则悄悄写作品记录；只读播放与共享记录修改分别评估。

建议第一版完整缓存小音频，大音频采用有界流式播放；跨会话的片段磁盘复用可后续再做，先避免缓存管理复杂度超过必要范围。后续仅在已确认资源版本且服务支持范围请求时保存可复用连续片段。范围请求使用 Range、核对 206 和 Content-Range；续传时有适用的验证器才用 If-Range。服务返回 200 表示完整内容时不能当作某个片段追加，版本变化后不能把旧片段接到新音源上。参见 [MDN HTTP 范围请求](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)。

没有可靠音源版本时，片段只属于当前播放会话，不跨作品自动复用；文件尚未完整时不能声明 SHA256 验证通过。完整音频哈希仅用于完整对象；片段以已确认资源版本、总长度、区间和验证信息标识，缺口不能当作已完整保存。不支持范围请求但格式能顺序解码时，仍可有界地顺序流式播放，不承诺跳播与断点复用；确实需要完整文件才能解码时，退回受限整文件获取，超限则提示用户选择永久保存或仅 NAS 保存，不能暗中突破额度。

播放网络缓冲有界，第一版预取最多当前音轨必要范围，不预取整个列表或下一页所有配乐。关闭播放器或切换作品取消无使用者的请求；同一音频还有其他正式保存任务时不随试听取消。暂停后短期保留会话，长期闲置释放连接，保留可验证的缓存。

应用磁盘缓存与 Chromium 内部缓存可能重复。媒体代理的响应缓存策略、网络会话与播放器解码内存必须测量，不能只数共享配乐目录。避免把音频转成 Base64 放进 SQLite 或通过 IPC 返回完整 Buffer；使用流式文件／受约束媒体协议。现有 `app-media://stream` 只处理视频，新增配乐播放需要专用解析和资源解析器，并不是换一个 `<audio>` 标签就能上线。

短配乐完整试听缓存可在同一会话循环时免于再次下载；大音源按需要范围循环，不每次从头下载整首。音乐条目时长、实际音频时长和作品片段长度分别保存，不能为了节省空间擅自截前 15 秒、改变速度或用同名曲替换。

### 去重、缓存命中和备份状态分开

作品可以保存“音乐信息已取得”，但本机音频处于未缓存、已缓存、已永久保存、已淘汰、暂不可播放等状态；NAS 是否有对象另记。试听缓存淘汰只改变本机缓存状态，不删除音乐绑定，不把图片完整状态改成失败，也不触发批量补齐。

同一精确音源版本下载由一个共享任务负责；按已验证内容版本复用，音乐 ID 只是候选查找依据。先登记等待者再启动，防止多个作品同时点开导致重复请求。下载期间合并 SHA256 计算；下载后相同哈希共用文件。不同音乐 ID、不同未知版本第一次取得文件仍可能各传输一次，不能把这一点写成“所有重复都绝不下载”。

身份未确认的试听来源短期绑定，不能无限保存每次 URL 变化的新版本；更新来源仅替换当前可用临时地址，不删除旧的已保存内容版本。音乐字段未返回保留既有有效信息，但展示上次核对时间；平台明确作品换配乐时创建新绑定，不覆盖其他作品仍使用的旧音轨。

临时签名地址属于短期获取信息，不作为去重主键，也不反复写入读取日志和全库历史。读取日志仍只保存作品差异必要字段，不把音频、完整接口响应或每次播放事件存进去。错误日志记录精简错误码、作品／对象标识及时间，采样或合并重复失败，避免空间优化后错误日志又增长数 GiB。

### 数据索引和后台处理

| 建议实体／索引 | 查询用途 | 防止的全库操作 |
| --- | --- | --- |
| 音乐条目主键：平台＋精确音乐 ID | 展示音乐基本信息、按 ID 找候选 | 不遍历全部作品找同名音乐 |
| 音源版本唯一键：平台＋已确认资源标识＋版本 | 合并相同源的获取任务 | 不把可变 URL 当无限新对象 |
| 内容对象主键：SHA256 | 按内容复用，查询大小、格式、可用位置 | 不为每个关联作品重新算同一文件哈希 |
| 作品配乐关系主键：作品 ID＋角色，反向索引：对象 ID＋作品 ID | 当前作品找音轨，音轨找全部关联作品 | 文件丢失时只更新受影响作品 |
| 本机保存关系：作品 ID＋对象 ID，反向索引：对象 ID＋作品 ID | 删除本地作品时判断其他正式使用者 | 不把收藏记录关系误算成本地永久引用 |
| 缓存清理候选：类别＋可清理状态＋访问时间＋对象 ID | LRU 分页淘汰 | 不在翻页时扫描整个音频目录 |
| 任务索引：状态＋重试时间＋资源版本 | 小批继续下载和失败补齐 | 不把几万任务全量推给界面 |

NAS 保存意图、当前引用、待提交引用和回执分开保存；不能用一个跨本机和 NAS 的总引用计数判断删除。若采用引用计数，关系表仍是事实依据，计数只能是可校验的摘要，崩溃后定向修复而非每次打开作品全量重算。

音频元数据随读取页已有事务写入，读取时不为每条作品再请求音乐详情。没有返回完整信息的只标未知；打开单条、手动补齐或明确保存时才按需要更新，避免把三万条读取变成三万次额外网络请求。

哈希、解码验证和目录检查在后台流式执行，单一数据库写入通道，UI 按 50 条分页；音频访问时间合并写入且不进入 NAS 变更日志。保存绑定与本地音频落盘分步骤可恢复，音频失败不回滚已保存图片或读取页。

## NAS 保存与多电脑恢复

NAS 现有对象按 SHA256 保存，适合复用相同音频：每个作品保留自己的配乐引用及片段参数，对象只上传一次，删除一个作品不能删除其他作品仍引用的对象。

但本地现有媒体路径检查要求文件在作品目录内，当前备份和恢复流程也按这一规则处理；共享配乐位于根目录统一目录，不能直接把文件路径塞入旧清单。建议增加明确的共享音频存储范围与统一资源解析器，供播放、校验、删除、备份和恢复共用，不能为了适配而关闭路径安全校验。

兼容路线先评估在现有作品媒体清单中登记 `audio` 及配乐绑定元数据，NAS 仍由各作品清单引用同一 SHA256；图片与配乐的完整状态分开，不能未经迁移就把音频塞进旧版限制的必需文件键。若另设共享音频记录，必须修改服务端支持的记录类别、校验及垃圾回收引用扫描。

NAS 0.2.2 的垃圾回收只认识作品的 `backupCover` 和下载清单里的 `assets`。已在隔离本机服务中证实：单纯添加新的配乐哈希字段不会保护音频对象，旧客户端恢复还会在各作品目录复制共享音频。当前服务拒绝 audio 必需键及独立共享记录类别。因此完整共享配乐方案需要服务扩展和客户端能力保护，不能直接上线；是否保持协议 2 仍待新旧客户端兼容测试决定，不要求清空 NAS。基础对象上传成功不等于 NAS 配乐功能已经实现。

新电脑先同步元数据，不自动下载整库配乐。选中恢复或播放时按需求取共享对象，本机已有有效对象就复用。恢复与永久保存的音频不能被浏览缓存清理淘汰。

### 仅在 NAS 保存的后续路线

用户如果希望长期保留几万图文的声音但本机不留整库文件，可选择“保存所选配乐到 NAS”。任务按已确认音源版本合并，在空闲时逐批执行：获取一小批 → 校验完整音频 → 上传对象 → 提交各作品引用与片段参数 → 确认同库同请求回执 → 释放没有本地保存引用的暂存。断线就停止扩大暂存，待确认对象受保护，重启后按检查点恢复。

NAS 中同一对象只保存一次，但不同作品的音乐版本和使用片段各自保留。“NAS 已保存”与“本机已保存”分开显示；重新听时可临时缓存，不能因听过又自动生成永久本地保存引用。一个作品删除 NAS 引用不破坏其他作品；服务端对象回收必须核对所有可识别引用、进行中任务和宽限期。

这个模式确实会取得并上传所选音频，仍有网络与 NAS 空间成本；只有用户明确选择后才运行。普通后台备份继续“本地有什么正式媒体就备份什么”，不因收藏里有音乐元数据就主动去抖音下载全库配乐。只有显式的“仅 NAS 保存”任务负责额外获取音频，两者要在 UI、任务状态与恢复行为上分清。

新对象引用在现有服务端提交与垃圾回收中均必须被识别，旧客户端不能删除或覆盖它。不能仅因为 `assets` 暂未限制 `kind` 就宣称旧版支持共享音频。第一版选择清单复用还是独立共享记录，要以旧客户端拉取、重新同步、删除、垃圾回收以及服务器能力协商的实际结果决定；必要时升级服务并提供迁移，不要求清空 NAS。能力不匹配时隐藏／禁用 NAS 配乐保存，保留已有内容，不用新字段绕过兼容检查。

## 删除与共享引用

删除某个作品的本地媒体时，解除它的本地配乐引用；其他本地作品或当前播放还在使用同一对象时保留文件。用户只保留收藏记录但已经删除本地媒体，不应因剩余收藏引用而永久阻止释放音频，也不能为了重新备份去抖音自动下载它。

共享音频下，还须按作品判断正式保存意图：先删除 A 的本机媒体，再删除 A 的 NAS 备份，即使 B 仍使用同一个本地音频文件，也不能因为共享文件存在而自动把 A 的音频重新备份。B 的引用和备份继续保留；A 只有再次明确保存或启动 NAS 保存任务才重新建立对应音频保存引用。试听 A 也不自动恢复它的永久保存意图。

删除 NAS 备份时只解除所选作品的 NAS 引用；别的 NAS 作品仍引用时保留对象。本地与 NAS 分别维护引用，不能混为一个引用计数。沿用用户现有规则：本地仍有该作品正式媒体就允许再次自动备份；已经先删本地再删 NAS 时，仅同步作品记录，不重新下载配乐。

崩溃和取消可能留下临时文件或无引用对象，建议使用有宽限期的后台清理，保护正在播放、下载和待提交文件，并在删除前重查引用。手动删共享配乐文件后，所有关联作品应明确标为配乐缺失；一次补齐可恢复多个引用，不能重复建立多个下载。

## 实施前的样本验证

至少核对同 ID 同音源、同 ID 不同片段、同名不同歌曲、原声或混音、无配乐、字段缺失、地址过期、平台不可用、不同 ID 相同文件，以及不同编码版本。每个样本记录音乐 ID、音源标识、音频实际时长、SHA256 和抖音实际播放对比结论；不保存账号密钥或完整请求凭据。

关键判定是音轨与作品实际使用的内容是否一致。本轮 7 条已确认网页音源字节相同，且有一条图文片段末尾的循环观察；手机端听感、非零起点与混音尚未确认。若某条响应只能取得音乐条目音源而无可靠作品片段，第一版明确提供“音源试听”，不能把它命名为已完整还原作品声音。

## 建议实施顺序和验收

| 阶段 | 交付物 | 上线门槛 |
| --- | --- | --- |
| 0 | 已完成首轮 12 条图文＋1 条视频对照的实时实验和脱敏报告；边界样本待补 | 普通直接音源路线已有依据，非零起点、混音和手机音量不作未验证承诺 |
| 1 | 与封面共用的缓存容量账本、对象保护和占用摘要；精简音乐元数据及绑定索引 | 读取不预下载，访问时间不进入备份日志，不重复已完成的大库性能改造 |
| 2 | 当前作品按需获取、试听缓存及唯一播放会话 | 必须同时有容量限制和取消；不能先上线无上限播放缓存再补清理 |
| 3 | 明确的本地永久保存、所选补齐、内容去重、续传和删除 | 图片完整与音频完整分别判定，共享文件没有误删和重复任务 |
| 4 | NAS 兼容、对象引用、恢复、删除、统计和能力协商 | 旧客户端不能毁损或回收新音频；不把未知支持当已兼容 |
| 5 | 仅 NAS 保存、断线小批暂存、确认释放、多电脑按需试听 | 必须验证回执未知、并发删除、库标识变化及预算无法容纳单音轨的行为 |

各阶段必须记录实际完成状态和测试证据。播放与缓存管理有依赖，不能只完成播放器外观就宣布可在数万作品资料库安全使用。

验收应包括：100 个作品使用已确认相同音源只下载和存储一次；同名但内容不同不合并；不同片段播放正确；取消某个等待者不影响其他作品；删除单个作品不破坏共享对象；断网及重启可继续；配乐失败不删除图片；跨电脑恢复不依赖旧机器路径；无整库预下载，操作期间无大字符串错误和明显界面阻塞。

还需要以下容量与性能验收：

1. 新读取三万条图文只增加元数据；仅打开一页不会请求全页所有音频，静音或未开始试听时不触发音频下载。
2. 连续试听大量不同音频后，缓存完成对象、片段、未完成文件及预留受同一预算控制；当前使用对象受保护时不继续无上限写盘。
3. 浏览缓存清理只改变缓存可用状态，图片、正式音频、作品与配乐关系、NAS 引用均保留。离线显示“未保存／未缓存”，不误报平台无音乐。
4. 同一音频并发被多个作品试听、保存或备份时，只用必要传输；取消一个使用者不影响剩余任务，正式保存不会被 LRU 淘汰。
5. 单音频大于试听额度、长度未知、Range 返回 200、过期授权、资源版本改变、解码失败、磁盘满均有有界回退，不反复下载整首。
6. “仅 NAS 保存”测试至少含三万作品／大量不同音源的任务模型，暂存不先落地整库；实际远端传输另用少量真实音频验证，合成测试不能替代音轨核对。
7. 分别记录本机和遵义机器的磁盘峰值、重复传输率、试听首声延迟、内存、事件循环延迟和取消响应；沿用封面方案的初始响应目标，不能把网络音轨加载时间算作 UI 卡死，也不能以能播放一次代替大库测试。
