# 网页进程崩溃排查与稳定性调整

## 已确认的事实

- 用户看到 Chrome `STATUS_BREAKPOINT` 崩溃页面。
- 本机最新两份 Crashpad 文件记录：Chrome 150.0.7871.187，`ptype=renderer`，异常 `0x80000003`，均位于 `chrome.dll + 0x42a2882`。只在本机解析了异常与模块信息，没有上传原始崩溃转储。
- 最近一轮保留 2569 条、307 个连续分页；前一轮保留 3235 条、396 个连续分页。两轮都没有服务器明确末页，不能把这些数字当收藏总数。
- 先前工具只记录 Runtime 超时，没有及时把网页原生崩溃与一般断线区分开。
- 现有信息不能证明是内存不足，也不能证明实验响应流命令单独造成了崩溃。

## 本次调整

1. 默认不调用实验性 `Network.streamResourceContent`，在 `loadingFinished` 到达时立即取正文，不在界面操作后排队取数据。
2. 默认轻量模式：滚动运行中不加载这个专用页面新的 Image / Media 请求。收藏 JSON、脚本、样式和账号验证流程不被主动改写。暂停后恢复普通请求；用户可取消勾选轻量模式。
3. 正常循环不再反复注入整段脚本；合并页面状态查询，保存每页记录时不等界面返回。
4. 识别 `Inspector.targetCrashed` / `Target.targetCrashed`，保存记录、标为未完成、停止对崩溃页面反复求值。旧页面未处理完的响应通过 epoch 排除。
5. 每 15 秒保存 JS 堆、DOM 节点、系统可用内存和记录程序内存的有界采样。高占用时保护性暂停，不假定已经读完，也不自动刷新重试。
6. 原有 JSON 保留，并另存最近两份到桌面 `收藏网页翻页记录/崩溃前记录-2026-09-28`。

## 验证与边界

- 19 项相关单元/DOM 检查通过。
- 隔离的真实 Chromium 窗口测试：12 个并发 gzip 响应完整收到；未使用响应流；轻量模式阻止图片请求、关闭后恢复；人为触发测试窗口崩溃时成功收到崩溃事件。该崩溃测试没有操作用户的实际收藏窗口。
- 新一轮真实网页轻量翻页已继续运行，检查到 2502 条、298 页时无新增错误。
- 新增资源采样显示约 1586 条时 JS 使用量约 622MiB、DOM 约 8.1 万节点。后续使用量随垃圾回收在约 318～1000MiB 间波动，JS 已分配堆和节点数仍增长。此现象说明长页面有明显资源负担，但不构成原生崩溃根因证明。
- 完整两万条长运行尚未通过，不能宣称彻底消除 Chrome 崩溃。
- 已询问用户是否增加“不展开全部卡片的稳定计数模式”，该模式尚未实施或启用；它将沿用登录网页逐页统计，需要明确区别于纯网页滚动核对。
